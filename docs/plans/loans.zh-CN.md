## 已确认与待配置边界

1. “军团/个人”指出借方；已确认两种出借方均支持，借款方为成员。个人出借需本人显式启用并指定付款角色，不因绑定角色自动成为出借方。
2. 已确认支持固定总利息与按期等额分期；每期分别保存本金和利息，最后一期吸收舍入差额，旧条款不随新配置重算。
3. 币种为游戏 ISK；已确认放款/还款接入游戏合同自动核验，不混入果壳币。
4. 固定总利息已确定；提前还款、逾期处理及还款抵扣顺序仍作为上线前需配置/验收的政策，不增加罚息或复利。
5. 已确认实现评分、额度、担保和抵押审批；评分阈值、评分到授信的映射、担保责任范围、抵押折扣和处置流程作为管理员配置，未配置前不批准贷款。

## 可复用部分

- identity：按本站账号识别自然人，具体收付款使用有效绑定角色；多开共用已确认要建立的信用额度。跨资金池的额度范围采用下方建议，仍待确认。
- approval：军团管理审批使用宿主注入的 reviewqueue.Source，只读聚合贷款模块的原单据；中心不保存第二套审批状态或账本。原服务端仍需对象鉴权，禁止借款人审批本人借款或取消。
- wallet / eve：合同缓存通过宿主业务接口读取，不访问模块私有 store；贷款不执行钱包自动扣款，合同核验成功后才登记放款或还款。
- 统一列表、弹窗、中英文词表、账号主角色显示与财务导航分组。

如果个人是出借方，出借人确认本人资金的借出属于交易对手确认，不自动授予军团审批或其他人的资金权限；个人操作入口与管理员审批中心的边界需要明确。

## 建议业务链路

申请 → 审核/约定条款 → 待放款 → 核实实际放款 → 还款中 → 结清。

批准不等于已放款。期限起点须随规则确定，不能在申请时就自动形成实际借款余额。还款未获有效证据不能直接扣减债务。逾期作为未还且超过约定日期的状态，不凭状态自动加罚息。

贷款条款与资金分录分开：保留本金、利息条款、双方账号/角色、实际放款、还款分配、余额和审计。金额以 ISK 最小单位整数保存。确定后的条款保存版本快照，后续规则调整不追改旧债。

## 实施边界

- 独立 `loan` 模块（暂定 ID），Go 私有 SQL/store；宿主注入身份、审批投影和所选付款证据服务。只开放已完成的权限目录。
- 写入使用 CSRF、版本、幂等、活跃账号锁及贷款事务锁；付款证据保存不可变快照。若复用合同，必须接入 EVE 跨模块唯一合同占用，不能让同一凭证重复证明放款、还款或福利交付。
- 网络同步与账务发布事务分离；定时核验如需要则复用 River，载荷仅业务 ID。缓存缺失不当作未付款证据，重复扫描不重复入账。
- 账号合并必须覆盖借款方和出借方权益、保留首次归属与审计；两端合并导致债权债务落到同一账号时需显式冲突处理，不静默抹账。解绑也不删除债务记录。
- 沿用现有管理员读取政策；普通成员仅可读取自己参与的贷款。未知对象、权限与证据方向拒绝，不使用页面隐藏代替鉴权。

## 首版验收清单

- 重复提交、核验重试、取消与放款并发、同一付款证据重复占用。
- 账号合并/解绑/权限变化不消除历史责任或形成重复资金记录。
- 中英文、桌面/手机、加载/失败/空状态；生产发布前补迁移、回退及真实游戏验收说明。

## 建议首版范围

以下按“军团或个人作为出借方、成员作为借款方”展开，仍待确认；若用户所指是借款方类型，须重写主体和权限设计，不能直接套用。

| 项目 | 军团贷款 | 个人贷款 |
| --- | --- | --- |
| 债权归属 | 指定军团 | 指定出借人本站账号 |
| 债务归属 | 借款人本站账号，接收角色作为收款对象 | 同左 |
| 申请对象 | 有效开放的军团贷款方案 | 同意参与出借的指定成员，首版不做公开撮合市场 |
| 条款决定 | 军团授权管理者按方案审核；改动条款须借款人再次确认 | 出借人提出/确认条款，借款人确认 |
| 放款人 | 军团配置允许的付款军团分部或代付角色 | 出借人有效绑定且明确指定的付款角色 |
| 还款收款人 | 条款中明确的军团钱包分部或指定角色 | 出借人的指定角色 |
| 管理操作 | 军团范围内授权管理者，借款人不能自审 | 借款人和出借人各操作自己的义务，管理员不代替出借人同意出借 |

一个本站账号的多个角色共用借款记录及额度检查。本站账号只是现有系统的人群归属单位，不声称能识别未合并的多个账号属于同一真实自然人。

首版范围补充信用评分、担保、抵押及人工处置记录，与无息/固定利息、分期、提前全部归还、部分还款、人工核验和逾期列表配套。暂不加入公开竞标、自由债权交易、自动扣款、自动变卖抵押物、罚息或复利。

## 申请与条款确认

成员申请只需：出借方、借款本金、接收角色、期数/期限、用途。能从已选方案获得的条款直接展示，不让成员重复填写。个人出借须明确出借账号，不能仅凭同名角色或 QQ 号识别对方。

提交时保存申请快照。审核可直接接受，或提出修改后的条款；本金、利率、还款日、期数、收款方任何变化均产生新版本并要求借款人明确确认，禁止后台修改后直接放款。

最终确认页展示本金、总利息、总应还、期数、各期金额、起息/到期规则、收付款对象；提交后版本冻结。后台政策变更只作用于新申请。

状态建议：`submitted` → `awaiting_acceptance`（仅改条款时）→ `approved` → `active` → `settled`；另有 `rejected`、`cancel_requested`、`cancelled`。逾期由还款计划推导，不覆盖主状态。付款待核验、争议、证据失效为独立核验状态，不把所有异常挤进主状态机。

## 利息与分期建议

首版建议整笔固定利息；尚未获用户确认。字段必须叫“本次借款利率”，不能将全期利率冒充年利率/月利率。

- 总利息 = 本金 × 本次借款利率，按 ISK 0.01 四舍五入；计算使用整数/有理数，不使用浮点累计。
- 还款计划分别分摊本金和利息到各期，最后一期补足舍入差额；两项合计必须与整笔条款一致。
- 示例：本金 100,000,000 ISK，全期利率 3%，分三期；总利息 3,000,000，总应还 103,000,000。每期本金前两期 33,333,333.33、末期 33,333,333.34；利息每期 1,000,000；应还额前两期 34,333,333.33、末期 34,333,333.34。
- 实际放款被核实后，按付款证据时间确定计划起点；延迟同步不能把起点改成同步时间。显示申请阶段的预估日期与生效日期区别。
- 建议按日历月分期，以首次实际放款日期的 UTC 日号为锚点，月末不足则取该月最后一天，下月仍使用原锚点；明确保存每期到期时刻，界面按语言/时区格式展示，不能只存“第几期”。非月周期如果需要则作为明确配置，不将 30 天和一个月混用。
- 固定总利息下，提前还款默认不自动减免已约定利息；若允许减免，必须有单独的出借方减免确认与审计，借款人看到新的结清报价后再支付。该提前还款规则同样待确认。
- 还款建议先处理最早未清期，再处理当期，最后归还以后各期；一期内先本金后利息，保存每笔分配明细。抵扣顺序是待确认政策，不由界面显示顺序隐式决定。
- 超额收款单独列为“待处理多付款”，不生成负债余额，不自动作为赠与、果壳币或下一笔贷款本金；退款需独立证据及审计。

如选择按剩余本金按日计息，必须在开发前替换本节：明确年化/日率、日界线、365/366 分母、付款生效时间、提前还款与迟到流水重算方式；不能同时上线两个未验收的计息引擎。

## 放款与还款对账

首版建议钱包转账、自动推荐、收款方确认；合同为待选方案。现有钱包读取是只读展示，不等于已具备贷款自动核销服务，需要新增规范化证据接口和占用检查。

1. 为每次放款或还款意图生成独立持久业务编号（暂拟 `LND-日期-UUID` / `LNR-日期-UUID`，UTC 日期），一键复制接收方、金额、备注编号。贷款本身另有稳定贷款编号。
2. 用户在游戏中完成付款；本站提交付款说明只进入待核验，不立即增加放款或扣减欠款。
3. 后台读取本地钱包证据，先检查官方流水类型的收付方向，再核对指定付款方、收款方/分部、金额、时间范围和完整编号。不能把所有 `first_party_id` 都统一解释为付款方。
4. 精确匹配优先推荐；同额或时间接近但缺编号仅列弱候选，多个候选进入人工处理。不得把钱包余额变化或网页上传截图单独当作自动核实依据。
5. 放款由借款人确认已收到；还款由出借人/军团授权管理者确认已收到。确认仍需合法证据，付款人不能确认自己的付款已到账。管理员调解属于独立审计动作，不伪装成对方确认。
6. 核实完成后同一事务写入证据快照、唯一占用、资金分录、分期分配和审计。单次付款首版只对应一笔贷款/一个付款意图，允许在该贷款内分配多期，暂不拆到多笔贷款。

钱包记录在不同凭据、付款方和收款方缓存中可能重复观察，先选定规范化收款侧钱包身份＋流水 ID 为凭证身份；不要把凭据 ID 或内容指纹作为可重复消费的独立凭证。同号内容冲突进入异常，不能作为第二笔钱入账；双方观察只佐证一次付款，不累加。首版统一收款侧证据，跨侧替代需要额外等价性设计。

放款首版建议一次足额；若发现真实部分放款，不丢弃实际金额，也不自动激活全额还款表，应冻结后续正常放款操作并进入部分放款处理，协商补齐或退回。处理完成前明确展示已核实付款和未激活条款，避免把金额差异藏成“未放款”。

还款可小于某一期金额，核实后按约定规则分配并保留余欠。系统不自动执行游戏付款。同步失败显示等待核验；款项已经到账但缓存迟到时，保留付款申报并标注“待核实”，不自动断言成员没有付款。补齐证据后按真实付款时间重算逾期展示。

采用合同方案时，须改为核对合同状态、精确收付方向、金额、接取角色、时间和完整编号，并接入现有跨模块合同唯一占用。当前混合/纯 ISK 合同仍有真实游戏验收缺口，不能因其他模块存在匹配代码就宣称贷款现金交付已经验证。

## 取消、逾期及异常

- 未受理且尚未形成放款授权的申请允许本人撤回；进入已批准/待放款后采用取消申请，冻结新放款意图，核对在途付款后由非借款人的出借方/授权管理者确认。
- 取消与放款核验共用事务锁；已经收到实际放款不能通过取消抹掉，应进入还款或协商处理。已观察证据的占用和审计不删除。
- 逾期显示逾期期数、逾期应还及天数；默认建议不追加罚息、不自动扣果壳币、不删除军团身份、不公开欠款排行榜。
- 展期、减免、错误证据更正需独立版本化操作。展期和其他义务变更由双方确认；付款更正用冲正分录和新证据，不直接覆盖原账。不得让借款人批准本人军团债务减免。
- 退团或解绑不免除历史借贷记录；若付款证据授权丢失，暂停自动匹配而不归零余额。换收款角色必须明确确认新对象，只作用于尚未创建的付款意图，旧证据仍按原对象核验。
- 到期提醒首版可放在本人工作台和军团管理待办；QQ/KOOK 外部通知尚未接入，不能写成已具备能力。

## 贷款池：管理可以出借的资金

建议按出借主体隔离资金池：军团池归对应军团；个人池归对应本站出借账号。两者可使用相同代码，但资金、债权、权限和审计独立，不能用一个人的回款偿付另一个人的池。一笔贷款首版只选一个池，不做多资方拼单或份额分红。

池配置包含：归属、名称、开放/暂停状态、允许申请人范围、付款/收款钱包主体、申请方案、负责人、资金版本。首版建议每个出借主体一个活动池，后续如需不同用途的池再扩展；不是自动给每个成员建立可公开借出的资金池，个人出借须本人主动启用。

资金分开记录：

| 指标 | 含义 |
| --- | --- |
| 累计注资/撤资 | 已登记并核实的本金投入和取回，保留原流水 |
| 池内本金现金 | 可作为本金出借的账面现金，含已预留但尚未付出的部分 |
| 待放款预留 | 已批准或等待借款人确认的有效条款占用 |
| 待撤资预留 | 已申请但尚未实际取回的池资金占用 |
| 可放款金额 | 本金现金减两类预留，暂停/冻结时不可新放款 |
| 在贷本金 | 已实际放款、尚未归还的本金，不算池内现金 |
| 利息收入 | 已实际收到的利息，单独记录，不与本金回收混淆 |

金额关系：`可放款 = max(0, 本金现金 − 待放款预留 − 待撤资预留)`。

注资核实增加本金现金；实际放款减少本金现金并减少对应预留；还本金增加本金现金并减少在贷本金；撤资实际完成减少本金现金并减少撤资预留。未收到的应收本金/利息不能当作可贷现金。

建议收到利息先放独立收益余额；出借方可显式选择转入池本金或提取收益，均保留审计，不默认自动复投。坏账标记不增加现金，账务核销与借款人债务减免是不同操作；首版不提供删除欠款入口。

池是本站的资金用途登记和可贷预算，不是 EVE 托管账户；本站预留不能冻结游戏钱包中的 ISK。已有钱包资金首次划入池须明确登记、责任人确认和可追溯证据，同一资金不能在多个池重复注资。新资金转入按所选游戏付款方式核验；不能读取钱包总余额就自动视为池金额。

同一钱包若承担其他军团支出，外部支出可能使账面池现金与实际资金不一致。对账异常暂停新放款，显示差额并由授权负责人调整/补资，不能自动减掉借款人的债务，也不能默默覆盖原池账本。首版推荐独立军团分部/明确指定个人资金角色，减少资金混用。

撤资只能预留可放款金额，不能提取已占用或已贷出的本金。暂停池不阻止已放款贷款归还与对账；注销有余额、预留或未结清债权的池应被拒绝。

## 信用额度：管理每个成员最多能借多少

建议按本站账号授信，所有绑定角色共用；额度表示允许占用的本金上限，不是账户余额或系统赠款。新增信用评分作为授信依据，按版本化规则生成建议，再由授权人员授信；评分本身不等于最终获批金额，不按 PAP/钱包余额直接换算资金。

建议一个成员共用一份系统总额度，覆盖军团和个人池；每个池可以给该成员设置更低的池内上限。这样不能换出借方或小号反复借满总额度。此为待确认的范围建议；若最终要求军团和个人信用独立，应明确改为独立额度域，而不是同时实施两个矛盾模型。

授信字段：成员账号、总额度、生效/到期时间（可选）、正常/暂停状态、理由、授信版本与操作者。分池额度归池出借方管理，不能由个人出借人提高系统总额度。总额度暂建议由站点管理员或后续明确的独立授信管理权限维护；借款人不得给自己提额，涉及自己的军团授信须另一授权人处理。

`已用总额度 = 所有池未还本金 + 有效待放款预留 + 对外担保责任占用`。

`剩余额度 = max(0, 授信额度 − 已用额度)`；如适用分池上限，则同时计算该池剩余额度。

`本次可申请上限 = min(系统剩余总额度, 分池剩余额度（如配置）, 池可放款金额, 方案单笔上限)`，同时满足方案最低金额、期数、未结清笔数及非暂停条件；新增增信规则后，还须通过下方“无担保信用＋有效担保＋已保管抵押”的覆盖检查。页面数值仅为当前参考，审批/放款前服务端仍需事务内重新检查。

没有有效授信时不可提交正式借款，可走独立“申请授信”流程；授信申请不会给池注资。信用审批不等于贷款审批，授信额度可高于某一时点的池现金，实际借款仍受两个上限共同限制。

还本金释放等额信用；支付利息不释放本金额度。逾期不自动扣更多额度，未还本金持续占用；建议逾期时暂停新借款资格，但正常接收还款。欠息是否持续阻止新借款作为明确规则执行，建议未结清逾期利息时仍阻止，不通过减本金余额掩盖欠息。

额度调低到已有占用以下时显示超额占用并阻止新增，不截断已有债务、不自动要求提前到期。授信到期/暂停只阻止新增承诺，已有合法放款、还款与证据继续追踪；已有未执行预留进入重新审核，不静默释放在途付款占用。

账号合并先合并两端债务和预留，授信额度不得相加；建议进入待重新授信并暂停新增借款，保留已发生责任。更换主角色或普通解绑不释放额度，不能通过删除身份资料清账。

## 信用评分与增信

### 评分用途与来源

建议使用可解释的 0–100 分规则，不采用无法解释的模型分。评分维度和权重由管理员配置，规则版本与数据时间一起保存。第一版可采用以下维度作为讨论基线，权重及阈值不是已确认参数：

| 维度 | 建议观察内容 | 防止误判或刷分 |
| --- | --- | --- |
| 借贷履约 | 已核实按期归还、逾期时长、未解决违约、担保代偿履约 | 只读真实付款核验结果；小额重复借还设贡献上限，不按借款笔数无限加分 |
| 成员稳定性 | 可核实的入团/绑定持续时长 | 使用已验证历史，离团重入不伪装连续；多角色不叠加时长 |
| 持续参与 | 联盟 PAP 按自然月是否达标、持续达标月数 | 账号所有角色合计后每月只判断一次达标，不按多开 PAP 无限加分 |
| 数据可信度 | 身份有效绑定、需要核验的数据是否齐全 | 不把手填 QQ/KOOK 当作已核实；同步失败按资料不足处理，不当作违约扣分 |

没有借贷历史标为“新人/历史不足”，不是违约；不默认给履约满分或零分。需为无历史情形配置基线和可用的担保/抵押通道。缺少历史月份时不自行补零：例如当前只有九月联盟 PAP，不能把未导入的八月当成未达标。

建议评分在核实还款、逾期更正、成员数据更新后重算，并有持久周期任务兜底；先生成新评分快照，再用于下一次授信/申请。展示总分、主要影响项、计算时间与规则版本，不展示其他成员私有财务数据。成员可以提出记录纠错，人工修正须有原因和审计。

人工决定应保存“系统建议”和“最终授信”两部分，不篡改底层还款事实来提高分数。改权重只影响后续评分/授信审核，不反向改写旧贷款利率、分期或已接受的担保责任。

### 分数、无担保额度与总额度

原单一额度升级为两个明确限制：

- **无担保信用额度**：主要依据评分和授信决定，可用于无需担保/抵押的本金部分。
- **总责任额度**：本人借款加对外担保的总风险上限；抵押/担保不能绕过这一硬上限。需要提高上限时先单独授信审核。

无担保额度按贷款冻结的无担保本金分摊占用；总责任额度按全部借款本金及对外担保占用。两个计数不能相互替代，不能因有抵押就把已有借款从总责任里删掉。

评分较高可申请信用贷款；评分偏低或无担保额度不足，可申请担保、抵押或组合增信。具体分档阈值及对应金额为配置，暂不预置真实成员分数。硬性冻结（未解决严重违约、证据争议、账号异常）不因有抵押或高分自动放行，需要明确的异常审核。

### 担保

- 担保人必须为有效本站账号，具有符合方案要求的评分、可用总责任额度和担保资格；本人及其绑定小号不得为自己担保。首版建议禁止循环担保，不开放借款人和担保人互相借用同一信用形成反复放大。
- 借款人选择担保人只是发出邀请，不立即扣对方额度，也不能冒充对方同意。担保人确认贷款、担保上限、期限、触发条件和责任版本后，才原子预留其额度；变更贷款金额/责任需重新确认。
- 首版建议担保仅覆盖明确的一部分本金，不默认无限连带利息或罚息；如需要担保利息，应另行定义责任上限及额度算法，不能在违约后临时扩张。
- 担保确认 → 放款前占用信用预留 → 放款后转为实际担保责任。未放款且无在途付款的合法取消释放；已放款后不能单方撤销担保。
- 一笔贷款可有多名担保人，但必须分配各自覆盖的本金，担保金额合计不能对同一部分本金重复计入增信。首版建议先限制为一名担保人＋可选抵押，降低操作复杂度；多人模式作为后续扩展，不能以多个邀请累计未确认额度。
- 担保代偿需出借方按已接受条款发起并审核，担保人完成游戏付款后按证据核实；不会从其钱包或果壳币自动扣钱。代偿入账时减少对原出借方的相应本金，担保责任转为借款人对担保人的追偿债务，保留原贷款关联；不能把代偿当作借款人全部免债或释放其全部总额度。

### 抵押

- 首版建议只接收本系统可以识别、核数量、估值并交付保管的舰船、普通物品和 PLEX；估价不完整、不可验证实例/数量、无法确定流通价格的物品不自动接受。是否接收配装舰船应按完整物品清单核对，不能仅凭配装名称认定价值。
- 只声明资产在借款人钱包/资产列表，或上传截图，不算已抵押。必须通过游戏中的明确交接交付至指定保管角色/军团主体，合同/物品证据核实后才进入“已保管可用”。游戏资产所有权不会因本站记录自动锁定，实际保管人为必要环节。
- 抵押审核保存物品清单、数量、估值来源/时间、折扣、核准担保价值、保管人、交接证据与唯一占用。可复用市场估价，但抵押折扣独立于福利补损折扣和奖励核价设置。
- 建议 `可抵押价值 = 完整市场估值 × 抵押折扣`，再按审批上限认定；折扣不得高于 100%，按类别配置，不擅自假定默认折扣。以吉他中间价作为参考时必须显式保留流动性折扣，不把估值当成能够立刻变现的现金。
- 缺价、过期报价或市场异常进入人工复核，不以零价替换历史估值。放款前重查足额与报价时效；放款后重估只能触发待处理缺口/补充抵押，不直接改借款本金、自动变卖或修改既有条款。
- 已保管实物及交接证据只能占用一次；可堆叠物品维护保管批次与已占用数量，不能只按 type_id 防重，也不能靠复制合同截图跨贷款重复质押。记录移动、替换、归还或处置均有数量守恒及审计。
- 清偿后进入“待归还抵押物”，保管人游戏交付、接收人/证据核实完成后才“抵押已释放”。首版建议整单债务结清后返还整批，不因一次部分还款擅自退走仍保护债权的物品。换押需先核实新抵押，再释放旧抵押。
- 违约处置需沿用借款人已接受的处置条款，由授权管理者审核并人工执行；实际卖出收入才可冲抵欠款，估值不计作回款。多余收入记为应退借款人款项，不足部分仍为未偿债务；不默认新增处置费或罚息。

### 组合覆盖与责任分配

审批为贷款本金 P 保存不重复的覆盖分摊：`P = U + G + K`，其中 U 为无担保部分、G 为已确认担保部分、K 为已交付保管的抵押覆盖部分；各项分别不超过可用信用/责任及核准抵押价值。一个本金单位不能同时靠多个来源反复计入覆盖。

例：申请 10 亿 ISK，可用无担保额度 3 亿；担保人确认并占用 4 亿；抵押物完整参考估值 5 亿，若方案折扣示例为 60%，核准覆盖 3 亿，则 3＋4＋3 覆盖该笔本金。60% 仅用于算例，不作为已确认默认值。仍需借款人总责任额度至少 10 亿、贷款池可放款至少 10 亿，以及最终审核通过；担保信用和抵押估值都不会给池增加现金。

担保/抵押完成前只允许“有条件批准”，不能创建可执行放款意图。最终放款授权在同一事务内校验：池资金预留、借款人额度、担保人确认和额度、抵押保管状态、报价与条款版本、非本人管理权限。缺少任一项均不得放款。

本金归还后，建议按批准时冻结的 U/G/K 比例分摊减少三类剩余覆盖，使用累计分摊并将舍入尾差固定分配，保证反复小额还款与一次还款结果相同；部分还款可减少担保责任，但实物首版保管至整单结清。具体释放顺序/是否允许部分提押在实施前确认，不能任意只释放担保而把风险转嫁给抵押保管方。

借款人的原债务、担保代偿、抵押处置、追偿、抵押返还分开记录。处置回款与代偿同时到达时按同一贷款锁下的剩余债权核销，超额列应退；不得双重收取同一欠款。代偿尚未核实不减少借款余额；担保被调用不等于已经收款。

账号合并、角色解绑、担保人降分或退出军团不解除已承诺责任。合并使借款人与担保人成为同一账号，或形成循环担保时，新增放款必须阻塞并由管理者处置；已发生债务和真实付款照常追溯，不自动抹账。

### 权限与展示

借款人看到本人的评分解释、可用无担保/总额度及“补充担保/抵押”入口；担保人看到邀请、担保上限、占用额度及自己的有效责任，不开放借款人无关钱包和其他贷款明细。信用分不做公开排行榜。

担保确认属于担保人自己的参与操作，留在贷款模块；军团授信、条件批准、抵押估值/保管异常及违约处置进入授权管理流程。借款人、相关担保人及存在个人利益冲突的保管者不能自行审批该贷款的军团风险决定；读取和写入分别鉴权。

推荐贷款页增加“我的担保”，抵押状态放入对应贷款详情；审批记录明确显示条件是否齐全，避免评分不足时只弹拒绝提示。模块必须能够解释为什么需要增信以及还缺多少覆盖金额。

## 资金和信用的共同占用

| 阶段 | 池资金 | 成员信用 |
| --- | --- | --- |
| 提交申请 | 暂不预留，显示参考额度 | 暂不占用，限制重复待审申请 |
| 审核通过/提出已授权条款 | 同事务预留本金 | 同事务预留相同本金 |
| 等待借款人确认 | 保留有期限的预留 | 同步保留；改金额时重新检查并调整 |
| 足额实际放款核实 | 现金转为在贷本金，释放对应预留 | 预留转为实际未还本金，总占用不重复增加 |
| 还本金核实 | 本金现金增加，在贷本金减少 | 释放归还本金对应额度 |
| 付利息核实 | 增加利息收入 | 不改变本金额度 |
| 无付款证据的合法取消/过期 | 原子释放预留 | 原子释放预留 |

提交多个申请不代表能全部借出；审批时锁定同一成员总信用、相应池/分池额度和贷款，统一锁顺序，只允许足够额度的事务成功。跨池并发也锁同一总信用，避免同一成员在两个池同时突破上限。

预留期限按方案配置。只有尚未授权实际付款、无已观察付款且满足取消检查的预留才能自动到期释放；一旦生成可执行放款意图或存在在途付款，不按定时器直接释放，转为待核实/取消审核。迟到付款仍须记录实际现金和债务事实，不能因预留已过期而丢弃，冲突时进入异常处理。

实际部分放款 X 时，只将 X 从现金转为在贷本金、从信用预留转为实际占用；剩余预留单独保留并进入异常，不把总申请本金重复占用两次。补齐或退款核实后再完成处理。

例：军团池本金现金 100 亿，待放款预留 20 亿、无待撤资，则可放款 80 亿。某成员总信用 10 亿、未还本金 4 亿、另一笔预留 1 亿，剩余信用 5 亿。即使池还有 80 亿，该成员本次最多申请 5 亿（若方案/分池上限更低则从低）。批准 3 亿后，池可放款变 77 亿，成员剩余信用变 2 亿；实际放款后上述可用数不再次减少；归还本金 1 亿后分别恢复至 78 亿和 3 亿。

## 其余可配置项

军团方案配置：开放状态、申请金额范围、允许期数、全期利率、同账号未结清笔数限制、预留期限、允许资金池、方案说明。具体值由管理员填写，不虚构默认额度或利率；不开放的方案不接受新申请。所有管理员调账/授信留痕，不开放浏览器直接写余额的接口。

个人池并不授权系统从个人游戏钱包自动扣款；由出借人逐笔确认金额和条款。任何开放出借列表应由本人明确加入，不把所有绑定成员自动公布为出借人，也不把借款人其他资方的明细开放给无关个人出借人。授信检查可返回可用/不足结论，明细仍按原权限控制。

## 页面与审批分工

财务与工具下新增一个“贷款”入口，页内区分“我的借款”“我的出借”；军团/个人用筛选或申请类型区分，不拆成重复的两个系统。普通成员只看参与记录；管理员查看范围沿用项目政策，管理操作仍需贷款权限和非本人检查。

列表保留：对方、类型、本金、未还本金/利息、最近到期日、状态、操作。详情使用统一抽屉或弹窗，展示条款、分期表、资金记录、审计；较长分期/流水只放详情，避免主列表每行展开大量文字。

申请/确认条款/还款申报使用统一表单弹窗；“申请还款”不等于执行游戏转账。军团管理审批集中到审批中心，贷款页保留本人记录与配置。个人出借确认留在“我的出借”，不让普通出借人因此进入现有管理审批中心；审批中心已有只读来源协议需要扩展贷款投影及详情组件。

工作台建议只增加本人“待还总额、最近一期、逾期”摘要；管理者待办复用审批中心计数。首版不增加无实际数据的收益图或装饰卡片。

追加贷款池与信用展示：本人页显示总信用、已用、预留、可用；出借/管理页显示池可放款、预留、在贷本金和利息收入。信用占用适合用一条有文字数值的分段进度展示，不将池现金与个人信用拼成一个余额；具体组件/排版留给实施时的页面设计。

## 数据与接口设计方向

暂拟私有表职责（未生成迁移）：

| 数据 | 内容 |
| --- | --- |
| loan_pools / loan_pool_entries | 池归属、资金状态、不可变注资/撤资/本金/收益分录与证据 |
| loan_credit_limits / loan_credit_history | 系统总授信、可选分池上限、状态、期限、版本和审批审计 |
| loan_score_rules / loan_score_snapshots | 可解释规则、来源数据版本/时间、分项贡献、人工修正与历史快照 |
| loan_guarantees | 担保邀请、责任本金、担保人确认、预留/生效/代偿/释放与版本 |
| loan_collateral_lots / loan_collateral_events | 物品保管批次/数量、估值、折扣、证据唯一占用及返还/处置记录 |
| loan_coverage / loan_recourse | 不重复本金覆盖分摊、代偿后的追偿关联及偿还记录 |
| loan_reservations | 贷款/撤资预留金额、有效期、付款授权状态；可追溯到原业务 |
| loan_policies | 军团方案及版本、申请限制、允许的资金主体 |
| loan_cases / loan_terms | 贷款主体、申请状态、已接受条款版本、双方身份快照 |
| loan_installments | 生效后每期应还本金/利息和到期时刻 |
| loan_payment_intents | 放款/还款方向、编号、指定收付款主体、预期金额、核验状态 |
| loan_entries / loan_allocations | 不可变资金/更正分录及每期分配关系 |
| loan_evidence / loan_audit | 冻结证据与处理记录，原始业务内容保留 |

跨模块付款凭证占用归证据提供方的共享契约，不能只依靠 loan 私有表唯一约束。账本只表达本站登记的债权债务与资金事实，不冒充游戏钱包余额。

建议 API 分为 context、policies、applications、terms acceptance、payment intents、evidence candidates/confirmation、repayment schedule、history。金额传十进制字符串，服务端转换为整数分；写请求有 UUID 幂等键与对象版本。不是一个允许前端任意改状态/余额的通用 PATCH。

资金池另有 pools、funding intents、withdrawal requests、reinvestment commands；授信另有 credit applications、credit decisions、limits、history。额度、现金和预留须通过分录/授权命令改变，汇总可缓存但必须能从有效分录及预留重建并对账。停用模块不遗漏池/授信/债务的账号合并参与服务。

相同请求键相同载荷返回原结果，相同键不同载荷冲突；金额核算与分配只在服务端执行。角色更换、条款改版、付款证据变化使旧确认令牌失效。付款证据被其他业务占用时必须拒绝并说明冲突，不能人工强制重复入账。

## 实施顺序与通过标准

1. 确认主体划分、固定/按日利息、钱包/合同付款；冻结池归属、总责任/无担保授信、评分规则、担保责任、抵押折扣/保管/处置、提前还款、收益复投及还款分配规则。
2. 实现资金池和信用底层：注资/撤资/收益分账、预留与现金/债务转换、总授信与分池约束、合并/冻结及不可变审计；再实现精度/舍入、条款版本和分期。并发申请/审批不得突破资金或信用两类约束。
3. 实现申请/双方确认、军团审批来源、本人借入借出页面及双语文案。
   加入评分解释与授信预览、担保人确认/额度预留、抵押交付保管、条件批准和最终放款校验，不能只实现分数展示而跳过责任流程。
4. 接入选定证据服务、规范化去重、放款/还款核实、异常与取消并发；账号撤权和同步中断不得误结清。
5. 验证本金 0/负数/超范围、零利率、三期舍入、月末/闰年、部分还款、提前结清、超额收款、证据同号不同内容、重复同步、多角色及合并冲突。
   同时覆盖：跨池并发授信占用、放款转换不双扣、还息不释放本金额度、还本同时恢复池现金和信用、下调额度不删债、预留过期/迟到付款、提现与放款竞争、收益未复投不得借出、重复注资证据、池暂停仍可还款。
   增信回归包括：缺失八月 PAP 不当未达标、无借贷历史不是违约、规则改版不追改旧条款、自担保/循环担保/合并冲突、担保邀请不占额度但确认后原子占用、同一抵押批次重复质押、缺价阻止自动放款、部分还款覆盖守恒、代偿保留追偿、处置超额退款及返还抵押证据闭环。
6. 用真实小额游戏 ISK 完成一笔经用户授权的借出与归还验证；未获授权不创建真实债务、付款或测试订单。验证后再安排生产迁移、启用权限、备份及回退边界。

当前首期交付已形成 Goose 70 和可选 `loan` 模块，并已部署到生产且开启 `MODULES`；真实合同、分期还款、审批中心聚合和生产账号验收仍按待办执行。此前“仅为方案完善”的表述仅适用于本方案早期版本。
