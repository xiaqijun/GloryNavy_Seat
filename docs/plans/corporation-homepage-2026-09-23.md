### 可核对的设计特征

- 黑色背景、偏米白文字和红色强调；顶部固定导航，有轻薄分隔线。
- 首屏占一屏，标题左置且尺寸很大，部分文字描边；右侧为客户端加载的场景区域。
- 主要内容按动态、数据、资源、活动、成员价值、渠道和招募逐段展开。采用大标题、编号、线性分隔及网格组合，减少圆角卡片套卡片。
- 数据区域使用醒目数字；招募按钮打开二维码弹窗。
- 源码包含约 0.85–1.05 秒的内容入场动画、加载进度界面和大量至少一屏高的区域。这些参数与本项目已确认的短动效、中等密度要求不同。

### 对上一版方案的调整建议

以此站作为主要构图参考，前面的 Brave 等站作为内容结构参考。以下建议仍待用户确认，不视为已批准变更全站风格：

1. 首屏从普通左右图文块改为**横向铺开的舰船主视觉＋左侧军团名称和短简介**；可以采用深色宇宙画面承托文字，导航右侧始终保留登录/工作台。
2. 图像允许越出原先的 45:55 硬分栏，主要内容仍统一对齐。桌面首屏建议约 70–85svh，并按短屏高度和实际文案适配，不强制每段占满一屏。
3. 下方介绍采用**大区块标题＋编号式特色列表**，代替三张相同的后台样式卡片；只有独立交互对象才用卡片。图像与文字交替形成层次，不靠增加口号和正文填满空间。

拟纳入首页的效果：

1. **首屏入场**：品牌标题与简短介绍分组淡入、轻微上移，仅首次进入播放；正文不逐字打字，登录入口无需等待动画。
2. **舰船景深**：指针移动或滚动时，舰船与远处背景小幅错位；不移动文字、登录按钮和招募按钮的实际点击区域。首屏离开视口后停止更新，触屏以静态布局为基础。
3. **分区呈现**：区块进入视口后一次性淡入；正常纵向滚动，不锁屏或劫持滚轮，脚本失败时内容仍可见。
4. **活动预览**：桌面悬停某项活动时，在固定图片区域切换对应舰队图片；键盘焦点提供同等反馈。手机直接显示相应图片，不把必要信息藏在悬停中。
5. **按钮与导航**：延续品牌色和短反馈；登录位置稳定，锚点选中状态明确。仅在适当的装饰区域尝试小范围光晕，不覆盖正文可读性。

现有全站规范规定 150–200ms 短动效。本方案建议宣传首页的一次性入场可放宽到约 400–600ms、层级错开约 60–90ms，**属于待确认的首页局部例外**；用户选定并批准方案后再记录到首页 UI 文档。后台动效参数不变。`prefers-reduced-motion` 下关闭入场位移、景深和跟随效果，直接显示最终内容；持续环境动效若后续加入，另提供关闭方式。

技术选型随最终效果确定：轻量状态反馈优先现有 CSS，入场用 IntersectionObserver；复杂滚动时间线才评估独立按需加载的动画库。3D 不是这些效果的必要前提。选型前不安装依赖、不改变现有路由动画或发布行为。

## 页面方案

### 1. 页头

- 左侧：现有官方军团图标与 GloryNavy 品牌。
- 中间：关于军团、成员支持、加入我们，均为本页锚点。
- 右上角：中英文切换、EVE 登录；已有会话时登录位置显示“进入工作台”。
- 使用独立公共布局，不挂载业务侧栏。

### 2. 首屏

- 左侧：军团名称、一句经确认的定位、最多两行简介，以及“加入我们”主要操作。
- 右侧：一幅舰船或舰队主视觉，图像占据足够面积建立 EVE 氛围；首屏不堆叠统计卡。
- “加入我们”定位到本页招募区域；登录保持在页头，成员可以直接进入。
- 沿用浅色底、品牌蓝、深灰文字，主视觉可以保留深色宇宙背景；不把全站改为深色或霓虹风。
- 优先复用已有官方军团图标。现有 `login-cruiser.webp` 是生成的概念图，可作装饰，不能标为军团实战截图或特定游戏船型；若选用真实舰队图，实施前核对公开使用范围与来源。

### 3. 军团与成员支持

- 一段简短军团介绍，接三个特色单元；候选为舰队作战、成长支持、成员福利，具体用词及公开范围待确认。
- 每个单元采用图片或图标、短标题、至多两行说明，不把已有系统菜单逐项搬上首页。
- 已实现福利功能不等于对外承诺无条件发放，不在首页公开后台额度、比例、申请人或财务数据。
- 公开简介第一版按静态内容维护；不新增新闻流、CMS、实时人数或战绩统计。

### 4. 加入我们

- 招募对象与必要要求采用短列表；只展示已确认的实际条件。
- 预留三步内容结构：联系招募人员 → 按指引完成申请/绑定 → 确认入团。准确步骤以军团实际流程确认后为准。
- 提供公开招募 QQ 群/KOOK 邀请或游戏联系人。未确认的号码、链接不填猜测值，也不从成员私人社区资料提取。
- 首版不新增站内招募审核系统。已有 SSO 绑定不代表入团审批完成。

### 5. 页脚

## 路由与认证方案

当前 `web/src/App.tsx` 先读取模块目录，再处理首页会话；`system.home` 的 `/` 当前对应工作台。匿名首页会跳到 `/login`。不能仅替换工作台组件，否则公开页仍被目录和会话检查阻断。

| 地址/状态 | 规划行为 |
| --- | --- |
| `/` | 公开军团介绍页；已登录也可浏览 |
| `/workspace` | 现有工作台整体迁入，保留 PAP、钱包、果壳币、管理员审批待办及权限边界 |
| `/login` | 保留登录失败、重新尝试与已有链接的兼容入口 |
| 其他业务页面 | 保留现有地址、模块声明、鉴权、资料完整度门禁 |
| 普通登录成功 | 资料完整进入工作台；需补资料进入原资料流程 |
| 绑号、重新授权、账号合并 | 保留各自结果页和错误恢复，不统一强行跳工作台 |

页头登录复用现有 `EveSignInButton` 的同源 POST `/api/v1/eve/login` 和官方 SSO 按钮资产，无需再点进一张居中登录卡。保留 CSRF、PKCE、state 等现有安全检查，回调 URL 不变，不接受任意外部回跳地址。

公共首页在私有模块目录/管理能力查询之前独立渲染。介绍内容不依赖 ESI、数据库或模块目录成功；登录状态检查失败只影响右上入口状态，不阻断介绍内容。只使用现有最小会话/登录可用性契约，不恢复匿名完整 scopes、版本、schema 或内部模块信息。

工作台导航、错误页“返回工作台”、品牌首页链接、测试及登录落点需一并核对；其中“首页”指公开介绍，“工作台”指 `/workspace`。部署必须验证 `/workspace` 直接访问与刷新正常，不能只验证前端点击。
