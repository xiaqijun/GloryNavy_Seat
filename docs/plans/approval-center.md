# 审批中心规划

> 历史阶段 / 方案记录：保留当时决策和测试结果，本文不是当前能力清单或最新部署指令。当前状态见[项目状态](../project-status.md)，尚未完成事项见[待办](../backlog.md)。

2026-09-21；状态：方案已实施为本地首版，尚未发布生产。基于生产 `v0.1.0-unified-fulfillment-20260921`。当前实现见[审批中心指南](../integrations/approval.zh-CN.md)。以下保留规划依据，具体接口与边界以指南为准。

## 目标与范围

新增统一管理入口 `/approvals`，集中处理待审批、待发放和交付异常。申请仍由成员在福利、损失和兑换页面发起；领域规则与状态继续归原模块。首版保留单人审批，不引入审批流设计器、逐级会签或领取任务锁。

| 来源 | 首版纳入 | 人工处理 | 自动处理 |
| --- | --- | --- | --- |
| 军团/PVP 补损 | 申请、取消申请、待付款、异常 | 审批、必要的金额核对、取消审核、游戏创建合同 | 核价、资格/出勤检查、合同关联核验、完成结算 |
| 成长福利 | 申请、取消申请、待发放、异常 | 审批、取消审核、游戏创建实物合同 | 技能及一次领取检查、物品快照核对、附带币结算；新纯币批准直接发放 |
| 超级航母/泰坦补贴 | 申请、取消申请、待付款、异常 | 审批、取消审核、游戏创建 ISK 合同 | 购舰合同证据/比例核算、付款合同核验 |
| 奖励兑换 | 取消审核、待发放、异常 | 取消审核、游戏创建合同 | 下单预留币、合同核验、完成或取消退款；正常订单不新增审批 |
| 历史纯币成长奖励 | 旧待发放记录 | 明确确认发放 | 原子入账与完成；不因接入中心补发 |

主动发币、规则配置、历史领取登记、PAP 发分及权限分配保留原入口，首版不新增审批制度；其现有审计仍保留。账号合并继续本人双账号 SSO 确认，不转为管理员代操作。联盟补损及普通旗舰暂停新申请，不因接入中心开放。

## 页面与交互

建议导航放在工作台下方，作为有管理权限人员的常用入口；菜单按真实可管理来源显示，不只针对超级管理员。沿用 Corporate Clean、统一图标、按钮和双语文案。

页头为标题和轻量计数，无大块统计卡。四个视图：

1. **待审批**：福利首次申请、取消申请；子筛选“申请 / 取消 / 待补充”。默认只列当前用户能处理的任务。待补充单独筛选，不计入可立即审批角标。
2. **待发放**：已批准福利、待交付兑换；显示“待建合同 / 等待同步 / 待接取 / 待确认发币”等真实状态。系统看不到合同只能称“等待合同同步”，不能据此断言管理员尚未建合同。
3. **异常**：金额/物品不符、多个候选、合同占用、发放方身份或权限待核实、证据不可读、旧快照不完整。等待 ESI 明细和等待成员接取是正常进度，不直接当作异常；长时间无进展可作为筛选，提醒阈值后续再配置。
4. **已处理**：审批/取消处理动作及最终完成、驳回、撤回记录；可筛选“我处理的”。人工批准的历史动作与当前待发放状态可同时存在，显示动作时间及当前状态，不把“批准”展示成“已发放”。自动完成标注系统处理。

筛选：业务类型、军团（仅有军团归属的来源）、人员、日期、状态，搜索业务编号/结算编号/角色名。兑换保持其现有站点级范围，不凭角色当前军团伪造历史订单军团；军团筛选不适用的兑换订单不混入结果。

桌面主列表铺满内容区，采用表格，列为：**类型与编号｜申请人｜项目或舰船｜金额或奖励｜待办状态｜时间｜查看**。申请人优先主角色，接收角色仅在不同时辅显；按本站账号识别，保留申请/交付角色快照和账号合并追溯。ISK 与果壳币分别标明单位，不相加汇总；实物显示简短名称及数量，完整组合放详情。

不将审批单拆成两列卡片。中屏隐藏可在详情找到的次要列；手机改紧凑记录列表，保持编号、人员、内容与状态可见。列宽按实际内容分配，长角色名/英文可换行，不把文字全挤在左侧，也不把整张列表收窄。

点行打开统一详情弹窗（复用现有 Modal），地址支持来源+ID深链接，刷新后仍可打开，关闭返回原筛选、页码位置和触发元素。不在首版引入另一套侧边抽屉样式。详情顺序：

- 顶部：类型、编号、人员、状态，突出此次需审核的内容。
- 自动检查：达标/出勤、重复领取、核价与购舰合同，仅展示与本单有关的简短结果；失败保留可行动原因。
- 奖励或核准金额、合同信息：复用已有快照与复制区。批准前隐藏创建发放合同操作，取消待审也隐藏新的发放信息复制入口，已关联证据仍可读。
- 原始证据与处理记录默认折叠；底部固定当前可执行操作。批准、驳回、取消、补充材料沿用统一紧凑表单，保存中禁止重复点击，失败保留输入，不在弹窗上叠第二层模态框。

正常批准默认使用已核验结果；人工改价仍要求明确选择及理由。驳回、补充要求、取消申请及取消确认理由沿用原校验，不为少文字跳过审计。

## 权限和并发

- 进入中心不授予业务权限。列表、计数、详情、动作均重新检查原模块当前权限及对象范围；不能先聚合所有记录再靠前端过滤。
- 福利沿用 `corporation.welfare` 及实际军团/对象范围；兑换管理沿用当前站点管理员检查。`access.manage`、`eve.sync.manage` 或游戏职务不替代这些权限。
- 本人申请不计入本人可审批数，不允许自审、自确认交付或审核自己的取消。成员查看自己的申请仍走原页面。
- **接入前需补齐差异**：当前 welfare 明确禁止自审取消；exchange.DecideOrder 的管理取消分支检查站点管理员，但未明确拒绝订单本人。实施时须在 exchange 原业务服务补齐本人限制及测试，同时覆盖旧 API，不能仅在审批中心隐藏按钮。该项已在本地原业务服务和数据库回归中落实。
- 首版采用现有版本号+幂等请求键。两名管理员同时提交，仅有效版本成功；另一方提示记录已更新并刷新详情。不开启批量批准、批量改价或批量确认取消。
- 取消审核继续与自动交付使用原事务锁：已完成发放不可取消；仍有效或证据不完整的合同阻止确认取消。人工在游戏核对未发放仍必需，缓存无合同不代表没有付款。
- 长期不处理的记录保持待办，不因超时自动批准、取消、退款或重建合同。

## 模块接入方案

拟新增 `internal/modules/approval` 与前端同名模块，由宿主注册来源适配器。首版为实时聚合查询与操作入口，不复制福利/兑换单据，不建第二套审批状态表，不新建付款或币账。

依赖关系：`approval → 宿主注入的来源接口 → welfare / exchange 的公开服务 → 各自私有 store`。approval 不直接读取其他模块 store，也不执行跨模块 SQL。详情渲染、来源查询及允许的动作采用明确注册表，未知来源/动作拒绝；停用来源模块不允许执行其动作。

来源接口拟提供：授权后的列表、分类计数、详情、允许动作，以及类型明确的命令调用。统一结果包含 `source`、`source_id`、`source_version`、原始业务状态、展示分类、账号与接收角色、内容摘要、金额单位、待办时间、允许动作及详情地址。展示分类不是新的业务状态。

前端复用各模块详情内容与表单，抽离现有 CaseView 等组件的路由依赖，避免审批中心与原页面各维护一套金额和资格逻辑。动作仍在原服务内复查权限、状态、版本、绑定、证据，写原流水与原审计；审批中心只传已登记的请求，不直接发币或改状态。

分页在服务端完成：来源私有查询先按授权范围及筛选获取有界候选，按稳定排序键合并；游标记录各来源已消费位置及筛选条件，不能把各来源第一页拼起来再假装全局分页。首版建议每页 30 条，待审批按进入待办时间升序、历史按处理时间降序，同时间以来源+ID破同值；源时间缺失时明确回退原单创建时间。计数由各来源授权查询得出，不能用当前页条数冒充总数。

列表仅使用已存储业务和同步数据，不为显示计数逐单请求 ESI。前台可见时约 30 秒刷新，操作后刷新当前单和计数；后台标签页暂停轮询。任一来源读取失败时明确标出该来源不可用及总计不完整，不显示为“0”；其余来源可继续浏览。

审计保存操作者、原单、动作、时间、理由、前后版本；历史继续取原模块日志，避免聚合中心重复写出两笔审批。后续若接通知或搜索投影，再经模块事件/事务 outbox 增加可重建索引，投影不得决定真实可执行动作。

## 原页面如何调整

首版交付时即明确区分成员业务记录与管理员处理入口，不将两套管理列表作为最终形态：

| 页面 | 保留 | 集中到审批中心 |
| --- | --- | --- |
| 军团福利 | 可申请项目、我的申请/领取记录、成员撤回/补充/申请取消、授权配置入口 | 管理记录、审批与取消审核、待发放和异常处理 |
| 兑换中心 | 奖品、我的兑换记录、申请取消 | 管理订单、取消审核、合同发放与异常处理 |
| 舰船损失 | 损失记录、补损状态、申请入口及关联申请详情 | 补损审核操作 |

成员不需要进入审批中心即可查看自己的申请进度、奖励、合同结果和历史。管理员在原业务页仍可按已有数据读取权限查看记录；该权限不因移除管理列表而扩大或缩小。移除的是重复的“管理记录”列表、审核按钮和发放操作，不删除原单、历史领取、防重复资格、合同证据或审计数据。

原页面和审批中心读取同一条业务记录，复用详情组件。原页面详情只提供当前成员可用的操作；有相应管理权限且可处理该单时，提供“前往审批中心”的深链接。审批中心负责管理操作，原业务 API 继续由各模块持有并执行同样的权限、版本与幂等检查；更换入口不能绕过原校验。处理成功后同步失效原页面列表、详情和中心计数缓存，避免显示两种进度。

规则仍在所属页面配置：补损比例/上限、成长项目、旗舰比例、奖励库不搬进审批中心。主动发币和历史领取登记等已排除的功能保持原入口。

开发期间可暂时保留旧管理入口用于核对；正式启用审批中心时，同一次交付完成重复入口收敛和旧管理深链接转向。旧链接按来源与原单 ID 跳转并重查权限，失去权限时明确拒绝，不转向其他人的记录。审批中心及业务来源按兼容配置一起启用，不能先移除旧入口而让管理员无处处理。

## 实施顺序与验收

1. **接入与只读列表**：原模块提供授权摘要/计数与稳定分页，注册来源、导航、四视图及详情深链接。先核对与原模块账单数量和状态一致。
2. **统一处理**：接福利审批、取消审核、旧纯币显式发放与兑换取消；补齐兑换禁止自审；抽离共享详情/动作组件，保持原校验和审计。
3. **发放与异常**：复用合同信息和自动状态，给出准确错误、来源链接及现有同步入口；不新增人工“标记已发放”、手动强制关联或跳过明细的按钮。
4. **回归及入口收敛**：同次交付移除原福利/兑换重复管理列表及审核/发放按钮，保留成员记录、申请和配置入口，验证旧链接跳转、跨页状态一致及权限；同时验证中文/英文、Chrome/Edge、320/375px与桌面、键盘焦点、错误重试、角色合并和权限撤销。随后按独立发布请求备份上线。

必须覆盖：同名角色不合并任务；账号多角色共享领取限制不变；同一单与取消申请不会在待审批重复计数；无权限来源不泄漏计数；页面刷新/翻页不遗漏或重复稳定记录；版本冲突不双审；合同完成与取消竞态不退款又发奖；重复调用不重复入账；缺价/未完成明细不被批准或结算；本人管理员订单仍不可自审取消；仅浏览中心不改变任何状态。

页面分工验收：普通成员无需审批中心权限即可查看本人历史及进度；原业务页不再有重复管理队列与审核按钮；授权管理者可由关联记录跳到中心定位同一单；中心处理后原页面状态一致；移除入口不删除历史数据、重置领取资格或改变管理员原有成员数据读取边界。

首版不做：审批流拖拽配置、金额多级会签、任务抢单、批量危险动作、QQ/KOOK 推送、自动审批。这些作为后续能力单独确认，不能把当前“自动核验发放”扩展为“自动批准申请”。
