# Corporation welfare

## Contract batch settlement (released 2026-09-30, Goose 57)

Administrators can select welfare and exchange records in the approval center's fulfillment view and create a contract-settlement batch. The server accepts only the `welfare` or `exchange` source and business record ID, and uses a `request_key` for idempotency. Goose 57 freezes the aggregate ISK/item snapshot and candidate recipient characters and generates a `BATCH-YYYYMMDD-UUID` reference. The administrator creates one in-game item-exchange contract with that reference. River reads the single contract, verifies the actual recipient belongs to the Seat account, issuer, whole-ISK amount, item multiset and completion state, then updates all batch entries in one transaction. Records containing Guoke coins remain on the original single-record flow; old batches keep their per-item compatibility path.

Each item records `pending`, `processing`, `completed` or `failed` plus its attempt count. A failed item does not roll back other completed items; the batch reports `completed`, `partial` or `failed`. Failed items with attempts remaining are retried up to three times, and an administrator can manually requeue them. Create, read and retry are administrator-only; the approval center remains a read-only aggregate and writes go through the welfare batch API. Goose 57 is active in production as `v0.1.0-contract-batch-merged-20260930`; real administrator mixed-batch, contract-claim and audit-closure checks remain a live acceptance task.

## Local update: personal reimbursement quota summary (2026-09-28)

It shows used, pending reserved and available amounts for today, this week and this month. Approval transactions include same-period pending reservations and exclude the case currently being approved. ## Per-account reimbursement period caps (released 2026-09-25, Goose 49)

Corporation SRP (`srp`) and solo PVP reimbursement (`solo`) retain separate corporation-scoped rates and per-claim caps. The same reimbursement settings now offer daily, weekly and monthly approved-ISK caps per site account (`loss_daily_cap_minor`, `loss_weekly_cap_minor`, `loss_monthly_cap_minor`, in hundredths of ISK). All cap fields may be left blank in the UI; blank saves as zero, and zero or omission means unlimited. No cap applies by default. Nonzero period caps must be at least 1 ISK. All characters on one site account share the cap; corporations and reimbursement kinds are independent. Only the site administrator can change these settings.

Periods use Beijing calendar days, Monday-to-Sunday weeks, and calendar months. An award belongs to its immutable first `approve` audit timestamp, not the case update time. Approved, executing, cancellation-requested and completed cases consume the cap; confirmed cancellations release it. Previously approved cases count in the current period when a new cap is set, but their frozen amounts are not recalculated. The server calculates the rate and per-claim cap first, then rejects an approval exceeding any enabled period cap; it never silently clips the payment. The existing welfare transaction lock serializes the usage check and approval, and account merges aggregate by current ownership. Goose 49 adds query indexes only; policy JSON and the audit table remain authoritative. Migration, Go service and frontend were released together; a live administrator cap-setting and over-limit approval check remains to be completed.

## PVP reimbursement submission and appraisal (deployed 2026-09-24)

Submitting a PVP loss first validates the bound character, killmail evidence and duplicate-claim rules, then persists the application and a `welfare.valuation-check.v1` River job in the same transaction. The HTTP save request no longer waits for Jita market quotes or purchase-contract reads. The initial valuation state is `pending`. The worker runs the existing versioned `appraise` command against the applicant's frozen loss evidence and records success, missing quotes or timeout in the case and audit. A minute-based scan recovers persisted pending cases missed during startup or enqueue. Repeated jobs only process still-pending PVP cases; a stale quote cannot overwrite a concurrent review or withdrawal.

Automatic approval still requires a complete matching quote; manual pricing requires an explicit choice and reason. If the market or contract source is unavailable, the application remains saved and exposes retry appraisal rather than using a partial subtotal. No migration, ESI scope or external worker service is added. Deploy the Go service with the new job kind; cancel unfinished `welfare.valuation-check.v1` jobs before rolling back to a binary that does not recognize it. Live production save and queue latencies have not yet been measured.

## Activity benefits (deployed with Goose 48; live fulfillment pending)

A site administrator creates corporation-scoped projects in the Activity Benefits tab. Each project selects one current reward-library package containing fittings, items, PLEX or ISK; its coin amount is configured separately. A per-character claim limit can be configured, with 0 meaning unlimited. Project and application snapshots preserve the selected library version and full contents, so later edits or archival do not alter pending cases. Projects have stable `activity_<id>` kinds and an enabled flag. `POST /api/v1/welfare/activity/projects` enforces administrator and corporation scope, optimistic versioning, and request-key idempotency.

A member can select multiple currently bound corporation characters in one submission, optionally write application notes, choose a personal contract as supporting material, and attach 1–3 JPEG/PNG/WebP screenshots (2 MiB each; 7 MiB request limit). The submitted contract ID is supporting evidence only: it is not treated as a verified purchase or delivery contract and does not replace later contract-fulfillment checks. The server creates one independent case per selected character, so approval, contract matching and claim history remain separate; the same notes, contract ID, image and reward snapshots are copied to each case. Each selected character consumes one claim batch independently; one character's claims never consume another character's allowance. Before publishing, the full selection is checked against the signed-in account and target corporation. The production reverse proxy must allow at least an 8 MiB request body for multipart overhead; the API still enforces the 7 MiB total limit. If the proxy remains at its 1 MiB default, larger screenshots are rejected with an HTML 413 before reaching the API, so the UI cannot show a structured error. `POST /api/v1/welfare/activity/applications` accepts repeated multipart `character_id` fields (a single value remains compatible with older clients). Each character's case, images and audit are saved in its own transaction, and the server derives a deterministic per-character idempotency key from `request_key + character_id`, so retrying the same batch does not create duplicates. Applicant-provided reward contents are ignored. `GET /api/v1/welfare/cases/{id}/images/{ordinal}` permits only the applicant or a currently authorized welfare manager and returns `no-store`/`nosniff` binary content. A reached character limit rejects new batches; cancelled or rejected cases do not consume the limit.

Activity applications use a dedicated transaction advisory lock. Only activity submissions serialize with each other for idempotent publication; they do not wait behind the welfare publication lock used by contract delivery, reimbursement approval or background verification, so a delivery scan cannot push an upload past the HTTP timeout.

Applications enter the existing approval center and cannot be self-approved. Coin-only awards credit atomically at approval. If any physical or ISK reward is present, staff create a directed contract in game with the persisted settlement reference in its description. Shared River delivery checks enforce issuer/recipient bindings, corporation, issue time, exclusive contract claim, exact frozen items and whole-ISK payment. Attached coins credit only in the contract-completion transaction. Pre-approval withdrawal and post-approval cancellation review follow the existing welfare rules. Goose 48 adds only the project sequence and image table, does not backfill old cases, and refuses rollback once activity projects or cases exist. The Goose 48 baseline is deployed; live game-contract fulfillment still needs validation. The current claim-limit, contract-picker and screenshot-preview updates remain local and are not deployed.
