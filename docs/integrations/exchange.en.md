# Nutshell Coins and unified redemption

Goose 58 adds an exchange-owned foundation for time-based alert consumption, with the frozen price version added in Goose 60, Seat-side administrator price configuration in Goose 62, and the persisted administrator switch in Goose 64. Seat reserves prepaid time using frozen `unit_seconds`, `unit_price_minor`, and `price_version`, settles confirmed non-overlapping intervals, releases unconfirmed intervals or unused allowance, and refunds settled intervals by the original reference. Sentry protocol v2 receives only `reserved_seconds` and an expiry, validates and reports server-confirmed intervals, and never receives pricing or coin amounts. A refund also reverses the grant's settled seconds and amount in the same transaction, so a corrected interval can be reserved again. Grant state and settled usage feed wallet accounting; releases and refunds are written to the coin ledger, while settlement details remain in the private consumption tables so the same reservation is not debited twice. Members can read the Sentry usage summary and frozen pricing records, and alert reserve/release/refund entries in the exchange journal link back to `/sentry`. The Sentry client now supports `alert-ack.v1` and complete `alert-use-evidence.v1` receipt evidence; the Seat Sentry client and River reconciliation worker understand the v2 seconds grant, delivery/consumption cursor, and state-mapping adapter. Site administrators can save the price version, pricing unit, Nutshell Coin price, grant cap and lifetime on `/sentry`; activation is explicitly controlled by the persisted `sentry_alert_pricing.charging_enabled` switch, which remains off by default until production pricing and isolated real-ledger acceptance. The host switch therefore remains off by default.

## Configuration and amounts

Site admins configure PAP coins per point (0.01–1,000,000, two decimals), integer ISK per coin (1–1,000,000,000,000), and SDE rewards with bundle quantity, ISK value, available bundle stock and listing status. Quantity is 1–1,000,000; bundle value 1–1,000,000,000,000; manually set stock 0–1,000,000. Type/quantity are immutable after creation; create a different listing for a different bundle. Rates start at 0/unconfigured, not 1:1. The `pap` (corporation PAP) and `alliance_pap` (alliance PAP) sources have independent rates; alliance PAP supports administrator-run monthly conversion and automatic snapshot deltas; the first character/month observation establishes a baseline. Administrators also select manual (Goose 26 default) or automatic conversion for sources that support it. Manual mode permits PAP issuance without a rate; conversion requires one. Automatic issuance rolls back PAP and coins together if a required rate is missing.

All coin storage and `*_minor` API amounts use integer hundredths. `minor_per_unit=250` means 2.50 coins per PAP. Reward cost is `ceil(bundle ISK * 100 / ISK per coin)` minor units, at least 0.01 coin. A 401 ISK bundle at 100 ISK/coin costs 4.01 coins. ISK is an administrator’s valuation, not an automatic ISK transfer or withdrawal promise.

## Manual and automatic conversion

PAP remains attendance history. Each event/character tracks converted units and its first actual conversion ratio; alts credit their original site-account wallet. Manual mode does not mint on PAP issuance or increases. A current site administrator opens the closed, awarded event, previews pending points and coins, enters a reason, and converts all pending points for that event. Corporation attendance managers alone cannot convert.

Automatic mode converts only newly added PAP. Switching modes never scans or backfills pending history. Admins may manually convert the remainder in either mode. Example: 4 PAP with 2 already converted, then switch to automatic and raise PAP to 5: only the new 1 PAP is automatically converted; 2 remain pending.

First actual conversion uses the current rate; later conversion or corrections on the same event/character retain that ratio. A quote binds the rate version and wallet snapshots. Stale quotes return 409. Reductions/revocations in either mode clamp converted units to valid PAP and reverse excess coins, retaining debt and journals. Unconverted reductions do not debit coins.

Legacy PAP and zero-rate placeholders are eligible for explicit manual conversion, never automatic historical backfill. Disabling exchange blocks additional credits but preserves reductions on existing awards. Re-enabling does not scan history. Manual conversion uses event, sorted account and source locks; converted units, coin journal and administrator audit commit atomically. Concurrent/replayed requests cannot pay twice, and the PAP statistics stay unchanged.

`POST /api/v1/exchange/sources` accepts `mode=manual|automatic`; omission preserves the stored mode for older clients. The `alliance_pap` source supports both modes; the first character/month snapshot does not automatically backfill coins. `GET /api/v1/attendance/events/{id}/conversion` returns a current-admin-only quote (`token`, `mode`, `points`, `converted`, `pending`, `coins_minor`, `unit_scale`, `characters`). Alliance uses the analogous `GET/POST /api/v1/attendance/alliance-pap/conversion` endpoint and reports PAP values in hundredths with `unit_scale=100`; the UI formats them as PAP. POST the same path with event or snapshot `version`, UUID `request_key`, quote `token`, and `reason`. Clients cannot supply arbitrary points, accounts or amounts. Session, CSRF, current admin and object policy remain enforced.

## Rewards and journal

An application claims one bundle for a currently bound character owned by the requester. Coins belong to the site account; changing main character or unlinking never transfers old currency/orders. Available coins equal effective source credits minus pending reservations and fulfilled spending, and equal the sum of all account journal deltas.

A transaction checks quote versions, ownership, listing, stock and funds, then writes the pending order, negative reservation journal entry and stock deduction. Administrators create contracts in EVE; verified completion marks fulfilled without another debit. Owners request cancellation; administrator approval after delivery checks restores coins and stock atomically. `fulfilled` and `cancelled` are terminal. Fulfilled refunds are not implemented. Item, bundle quantity, recipient, valuation and coin price are immutable order snapshots. Repricing or delisting leaves existing orders intact. Stock is unreserved bundles and may increase on cancellation. No ESI asset movement, delivery-contract creation or payment is performed.

## Boundaries and API

The host enforces session, profile and CSRF gates. `exchange.self` is only the entry capability; member endpoints check ownership. Rate/item configuration, SDE configuration search, fulfillment and all-order reads check the current site administrator. Corporation attendance, EVE roles and access.manage do not substitute; no assignable exchange-management capability is exposed.

The host registers `pap` and `alliance_pap` as independent sources. Unknown sources are rejected; there is no browser arbitrary-credit API. Attendance sends entitlement snapshots via a transaction-scoped injected business callback without importing exchange’s private store. Future sources need stable entitlement references, previous/new units, immutable account attribution, atomic correction semantics, explicit host registration and migrated rate configuration. This is not runtime script loading.

Private tables: `exchange_shop_settings`, `exchange_rewards`, `exchange_redemptions`, `exchange_shop_audit`, `exchange_source_rates`, `exchange_source_awards`, `exchange_coin_ledger`. PAP locks the event and sorted PAP accounts, then sorted coin accounts and source rate/entitlements. Claims lock current identity binding, coin account, valuation settings and reward. Decisions lock coin account/order, then reward for cancellation. No network calls occur inside write transactions. Audit/idempotency and business changes commit together.

Routes under `/api/v1/exchange`, detailed in [OpenAPI](../../api/openapi.yaml):

- `GET /context`: own recipients and registered source ratios.
- `POST /sources`: administrator source ratio; id, minor_per_unit, version and UUID request_key.
- `GET /wallet?before=`: own credit/adjustment, reservation and refund journal, 30 rows descending.
- `GET /rewards?after=`: own balance and listings, 30 rewards ascending; admins see disabled listings.
- `POST /rewards/rate`, `POST /rewards/items`: valuation and reward configuration.
- `GET /rewards/types?q=`: active local SDE ID/name substring search, 2–80 characters, at most 30 results; no ESI.
- `POST /rewards/claim`: own current recipient, one reward, current quote versions and key.
- `GET /rewards/orders?scope=mine|all&before=`: own/default or site-admin all orders, 30 descending.
- `POST /rewards/orders/{id}`: cancellation request/review, version, note and key.

Writes require CSRF, UUID idempotency and versions. Identical retries succeed; changed bodies or stale versions conflict (409). `insufficient_coins` means insufficient available currency, `reward_unavailable` means unconfigured/disabled/out of stock, and unauthorized objects return 404. Retry ambiguous network outcomes with identical key/body; close stale quote forms, refresh and reconfirm. Currency is not filtered by PAP report dates.
