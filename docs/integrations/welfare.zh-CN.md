# 军团福利

## 合同批量结算（已发布，2026-09-30，Goose 57）

管理员可在审批中心“待发放”视图勾选当前页的福利和兑换记录，创建一个合同结算批次。服务端只接受 `welfare` 或 `exchange` 来源及业务记录 ID，使用 `request_key` 幂等；批次与明细保存在福利模块私有表中。批次限制为同一本站账号组，同组多个 EVE 角色可以一起选择。Goose 57 起，创建批次时会冻结总 ISK、物品多重集合和候选接收角色，并生成 `BATCH-YYYYMMDD-UUID` 合同编号；管理员在游戏中创建一份物品交换合同，描述填写该编号。River 按编号读取合同，核对实际接收角色属于该账号、发放方、整数 ISK、物品明细和完成状态，完成后在同一事务内更新批次全部明细。含果壳币的记录暂不允许合并，继续走原单据流程；旧批次没有聚合编号时保留逐笔兼容路径。

明细分别记录 `pending`、`processing`、`completed`、`failed` 和尝试次数；某一项失败不会回滚已经完成的其他项，批次会显示 `completed`、`partial` 或 `failed`。失败明细最多自动重试三次，管理员可对未耗尽次数的批次手动重试。创建、读取和重试均要求站点管理员；审批中心仍是只读聚合，写操作通过福利批次接口完成。Goose 57 已在生产执行，发布版本为 `v0.1.0-contract-batch-merged-20260930`；真实管理员混合批次、合同占用和审计闭环仍需现场验收。

## 本地更新：个人补损额度摘要（2026-09-28）

补损页的个人额度摘要按本站账号、当前军团和补损类别计算，展示今日/本周/本月已用、待审批预占及可用金额。待审批预占使用当前可得核价金额套用冻结前的补损比例和单笔上限；仍处于核价中的 PVP 申请不虚构金额。审批事务会把同周期的待审批预占一并计入，批准当前案件时排除当前案件自身。统计读取与审批检查使用相同的周期和有效状态，未设置上限显示为不限。审批中心仍只负责管理员待办，不复制额度配置。

## 成员补损周期额度（2026-09-25 已发布，Goose 49）

军团补损 `srp` 与 PVP 补损 `solo` 继续按军团独立配置折价比例和单笔上限，新增同一“补损设置”内的每本站账号每日、每周、每月核准总额（ISK 分；`loss_daily_cap_minor`、`loss_weekly_cap_minor`、`loss_monthly_cap_minor`）。单笔与周期额度在界面可留空；留空保存为 0，填 0 或省略也表示不限制，默认不设任何额度。周期额度非零时至少 1 ISK。管理员可单独启用任意周期，不新增全站配置中心。一个本站账号的全部角色共用额度；两种补损和不同军团互不占用。

周期按北京时间自然日、周一至周日、自然月，以 `welfare_audit` 首次 `approve` 时间归期，不用会随交付变化的案件更新时间。当前状态为已批准、交付中、取消待审或已完成的金额计入；确认取消的案件不再占用额度。设置新上限时，当期已核准历史也计入，但旧单金额和策略快照不重算。比例及单笔上限先计算核准额，再检查全部已启用的周期额度；超额拒绝本次批准，不自动截断发放金额。检查在既有福利事务锁内执行，重复请求按原幂等规则返回，账号合并后按当前归属汇总。Goose 49 只增加额度查询索引，配置复用现有 JSON 与审计表；前后端与迁移已同版发布，真实管理员额度设置和超额审批待现场验收。

## PVP 补损提交与核价（已发布，2026-09-24）

成员点击提交后，服务端先验证绑定角色、击毁记录及防重条件，在同一事务保存申请与 `welfare.valuation-check.v1` River 任务，立即返回案件。不会在 HTTP 保存请求内等待吉他市场报价或购舰合同读取。初始核价状态为 `pending`；后台按申请人原角色和冻结损失证据执行原有版本化 `appraise`，成功、缺价或超时结果写入案件与审计。每分钟扫描持久待核价案件补捞启动期或入队遗漏，重复任务只处理仍为 `pending` 的待审 PVP 案件；并发审核/撤回后的旧报价不能覆盖新版本。

自动批准仍要求完整、可核验报价及金额一致；管理员人工核价必须明确选择并说明原因。市场或合同不可用时保留申请，显示核价失败及“重新核价”，不以缺价小计发放。无新迁移、scope 或外部后台服务；发布时须同步更新 Go 服务，回退到不识别 `welfare.valuation-check.v1` 的旧程序前先取消该种未结束任务。真实生产保存耗时与队列完成耗时尚未测量。

## 活动福利（已发布，Goose 48；真实发放待联调）

管理员在军团福利的“活动福利”页预设项目，引用当前奖励库中的一份舰船、物品、PLEX、ISK 组合；果壳币数量在活动项目单独配置。可设置项目名称、是否开放申请和每个绑定角色的领取次数上限，填 0 表示不限制。奖励库版本和完整内容冻结在项目配置中，成员提交时再冻结到案件；之后修改或停用项目不改动已有申请。新增项目采用稳定的 `activity_<id>` 类型，`POST /api/v1/welfare/activity/projects` 使用版本号、`request_key`、站点管理员及军团管理范围校验。关闭项目停止新申请，不删除旧记录。

成员可一次选择多个本军团已绑定角色，填写可选的申请说明，选择一份个人合同作为整理材料，并上传 1–3 张 JPG/PNG/WebP 截图（每张最多 2 MiB，总请求最多 7 MiB）。合同 ID 只作为申请人提供的辅助材料保存，不代表本站已核验采购或交付合同，也不会替代后续合同发放核验。一次提交会为每个角色创建独立案件，分别进入审批、合同核验和领取记录；同一批次对每个选中角色各计算一次，角色之间互不占用次数，截图、说明、合同 ID 与奖励快照复制到每个案件，后续处理互不混淆。合同选择器支持按描述或 ID 搜索；服务端仍以当前登录账号和项目军团范围校验角色。生产反向代理必须允许至少 8 MiB 请求体，为 multipart 开销留出空间；接口仍执行 7 MiB 总量限制。若代理仍为默认 1 MiB，较大的截图会在到达 API 前返回 HTML 413，前端无法显示结构化错误。`POST /api/v1/welfare/activity/applications` 接收重复的 `character_id` multipart 字段（旧客户端传一个值仍兼容），每个角色在独立事务中保存案件、截图和幂等审计，并以 `request_key + character_id` 生成角色级确定性幂等键；重试同一批次不会重复创建。截图为福利私有 `bytea`，`GET /api/v1/welfare/cases/{id}/images/{ordinal}` 仅允许申请人或当前有权管理该军团福利的人读取，响应 `no-store`/`nosniff`，不生成公开地址。达到角色领取上限时拒绝新的批次，取消或驳回的案件不占用次数。

活动申请使用独立的事务 advisory lock，只在活动申请之间串行化幂等发布，不等待合同交付、补损审批或后台核验共用的福利发布锁；因此后台交付扫描不会把上传请求拖到 HTTP 超时。

活动福利进入现有审批中心；申请人不能自审。批准后，纯果壳币项目在批准事务内到账；包含任一实物或 ISK 时，管理员在游戏创建与冻结内容精确一致的定向合同，将本站结算 ID 原样写入描述。共享 River 核对发放方、接收角色、军团、签发时间、唯一合同、物品与向下取整的整数 ISK；合同完成后才在同一事务发放附带果壳币。待审可撤回，批准后走取消申请及非本人审核；已完成不得取消。原福利单、币账、全局合同占用及审计仍各由原模块持有。Goose 48 只新增项目序列和截图表，已有福利数据不回填；出现活动项目或案件后 Down 会拒绝丢弃其结构。Goose 48 基线代码已发布生产，真实游戏合同闭环仍待联调；本轮领取次数、合同材料选择和截图预览更新尚未部署生产。

## PVP 自动核价（2026-09-19，本地）

PVP（`solo`）新申请自动生成核价快照，仍须人工审核，不自动批准、付款或完成。军团补损继续使用人工核准金额及有效出勤门槛。旧申请不后台补写，待审单可点“重新核价”；已批准及已完成单不重算。

- 有购舰合同 ID：只读取申请角色已同步的个人合同，沿用合同对象权限。必须是 `item_exchange`、精确 `finished`、购买角色匹配、完成不晚于损失、完整物品包含一艘对应船型、无索取物品或奖励。按合同总价核价，不套市场比例；多船、缺价、零价或异常合同转人工核价，不悄悄改用市场价。合同只能证明采购，不能证明这就是损失的同一艘船，仍由审核人核对。
- 未填 ID：以服务端保存的击毁报告为准，核价范围为**船体一艘＋全部物品**，包含装配、货舱、无人机、弹药及嵌套容器内容；数量为毁损＋掉落。复用 market 的吉他 4-4 买一/卖一均值和统一比例，按类型 ID 取价，名称仅作展示。采用核价时可用行情，不是损失发生时的历史行情；特殊装配属性、蓝图副本价值等需人工核对。
- 缺少任意物品双边报价，不使用已知小计作自动核准金额；缺报告或服务不可用也不阻止受理，但显示待核价。可重新核价或由审核人明确勾选“人工核价”并填写金额、原因。零折算金额同样转人工处理。
- 自动核价审批只接受已保存的完整核价金额，客户端自报快照/改价无效；人工模式保留原快照、实际核准金额、原因和审核人。原自审限制、KM 防重、版本校验及幂等仍生效。
- 快照保存明细、来源、行情时间、核价时间、比例及配置版本或购舰合同内容；刷新仅限待审 PVP 单，本人或有范围权限的审核人可操作，历史快照留在原审计。购舰读取不扩大审核人的个人合同权限；刷新缺权限时可由申请人更新或人工核对原证据。

`POST /api/v1/welfare/commands` 新增 `action=appraise`（id/version/request_key/note），`approve` 新增 `manual_pricing`（默认 false，仅 PVP 生效）；`detail.valuation` 与 `detail.pricing_mode` 由服务端生成。缺完整自动核价或金额不匹配返回 409 `welfare_valuation_required`。行情网络请求在写事务前、使用共享 ESI 缓存与预算，补损核价最多 8 秒（预留 HTTP 写入时间，独立估价工具仍为 25 秒）；失败明细可通过重新核价重试。批准后原“推荐交付合同→人工确认→完成状态核验”不变。

无需新增迁移；启用 market 并完成 Goose 36 才能调用市场估价。停用 market 保留已有证据和人工核价，购舰核价仍可用。账号合并随福利案件一起迁移，原审计不改写。请保持匹配前后端，不回退至丢失核价证据的旧程序。未发布生产，真实补损审批和游戏交付仍待业务联调。下文人工金额描述是此前阶段口径，PVP 以本节为准。

## 初次配置

## 申请、审核与交付

补损页仅向当前站点管理员显示“手动录入”，不保留成员申请按钮；军团福利管理权限不能替代管理员身份。成员从独立 `/losses` 选择已同步报告申请补损；成长福利与旗舰补贴保留普通申请。手动录入仍限操作者本人有效绑定角色，未开放代成员录入。后端在录入前及发布前重查管理员，`synced_loss=true` 必须有真实本地证据，不能靠该标记绕过。已有单据的补证和撤回规则不变。

成员选择本人有效绑定角色，通过本地 SDE 搜索舰船，填写损失/合同/活动编号、时间、简要说明和证据文本或链接。成长申请从规则取得指定船型。关联配装、技能方案时保存读取时的配装及技能检查快照，不将其当作损失瞬间实装。

Goose 32 可从“舰船损失”选择本人受害报告，将舰型、时间、星系及物品保存为申请证据，服务器重新校验并采用已同步字段。活动、合同编号、KB 估价及付款/合同接取凭证仍由负责人核对；考勤关联和合同完成核验见上方当前规则；KB 估价仍未自动抓取。额外证据以文本/链接登记，没有附件上传。技能未达标或缺样交负责人说明处理，不自动发船。普通旗舰的具体适用舰型由公告和审核核定；系统禁止以普通旗舰渠道申请泰坦/超级航母，不能用此分类校验代替购舰审核。

流程：待审核 → 待交付 → 交付待核对 → 已完成。待补充、待联盟结论、驳回和撤回分别留痕。成员只能撤回未批准申请；待补充时可补证后重新提交。有业务权限的人员先批准，再领取交付任务，在游戏内操作后填写实际付款或合同接取凭证完成。本人申请不能由本人批准、执行或确认交付。

尚未领取交付任务的“待交付”申请可由负责人撤销批准并释放资格。进入“交付待核对”后不允许直接取消、释放或再次安排付款，以免外部结果不明造成重复交付；交付异常、已完成 ISK 差额/追退与历史档案误录纠错的专门流程仍待后续扩展，不能通过删流水处理。

核价使用整数百分之一 ISK，保留到 0.01 ISK（不足最小单位舍去）：

| 项目 | 计算及限制 |
| --- | --- |
| 军团补损 / 历史联盟补损 | 人工填写实际核准金额，不按旧福利固定比例折算或自动限制日次数 |
| PVP补损 | 购舰合同价优先；未填则船体＋全部物品中间价 × market 统一比例；人工审核，可明确选择人工核价并说明原因 |
| 成长舰船 | 四舰型每主体各一次，实际接取由负责人核实完成，金额不是零元 SRP 基数 |
| 普通旗舰 | 核准购舰基数 × 10%；占用三个尚未使用的有效 Active 月 |
| 大航 / 泰坦 | 分别 × 10% / × 5%，各一次；每次购舰凭证与船型组合只占用一次 |

同一 KM 只有一个有效主补偿，不因角色、账号、渠道不同重复领取。补损不再使用 PVP 日限或身份核验门槛。7 日申请建议未硬编码。购舰暂按“合同 ID＋船型”防重，同一合同内同型多船需另行人工厘清，未做购买单元拆分。

## 主动发放果壳币

仅当前站点管理员可发起，与 PAP 无关。选择单人或最多 100 个成员，填逐人币数及原因，预览人数和总额后确认。同账号多个角色只显示一个成员选项；后端拒绝重复账号。金额为 0.01–10,000,000,000 币/人，采用整数最小单位，不能提交负数或超精度金额。

发放单、exchange 来源权益、币流水和审计同事务发布。来源固定为 `welfare_grant`，来源引用为发放记录 ID；不开放任意钱包加币接口，不使用或修改 PAP 比例。每个成员只读本人单据，不会从批量发放审计看到其他成员金额。跨角色不能增加同成员的本次发放次数。

误发可由管理员全额冲正原发放，必须说明原因。原发放金额和流水不删除；冲正后状态为已冲正，原权益余额归零。已消费时可能形成欠额并按 exchange 规则阻止消费，不撤销已有兑换订单。当前仅全额冲正，没有部分冲正或通用冻结管理。底层币服务拒绝停用 exchange 时新增发放，并保留旧权益冲正能力；当前 welfare 的运行依赖要求 exchange 同时启用，因此停用 exchange 也需停用福利入口，页面冲正需恢复依赖后操作。重新启用不补发。

## 身份、权限与合并

福利历史按本站账号和原归属保存，复用显式账号合并作为成员归并流程；本版没有另建可独立合并的自然人 membership 平台。成员核实是人工步骤，QQ/KOOK 和同名不触发自动合并。换主号或解绑不刷新一次性资格。

`welfare.self` 仅是入口能力；对象接口另外校验本人归属或军团管理范围。新增可委托 `corporation.welfare` 为福利审核与交付，按军团/联盟筛选授权；它不从 CEO/Director 游戏职务自动获得。规则、历史核验、主动发币和冲正仍要求站点管理员。站点管理员可以读取有效成员记录；管理列表按当前有效绑定军团成员过滤，本人可读取自己已有的历史申请。此能力不授予全部合同、ESI 或军团财务读取权。

福利合并服务始终登记，包括关闭福利 UI 时。预览摘要包含福利记录数及变更指纹；预留资格重叠或与对方历史领取冲突返回 `merge_business_conflict`，先处理待交付申请再合并。已完成记录全部保留、资格取并集，原审计与首次归属不改写；Active 月份去重，重叠月份不重新发资格。合并后身份/历史可能需要重新核实。此版本以原始账号记录及合并链追溯主体，而非规划中独立的 `beneficiary_id` 表。

锁序：已有角色锁（涉及接收角色时）→ identity 活跃账号共享行锁，账号按序 → welfare 发布锁 → 币账号锁及来源权益。所有 welfare 写事务使用一个短期模块锁保证规则、资格与幂等串行发布；外部数据读取在事务前。本版没有网络付款、队列作业或长时间持锁计算。

## API 与发布

完整结构见 [OpenAPI](../../api/openapi.yaml)，统一前缀 `/api/v1/welfare`：

- `GET /context?corporation_id=`：可见军团、本人角色、管理员标志、所选军团规则。
- `GET /ships?corporation_id=&q=`：本地 SDE 舰船搜索，2–80 字符。
- `GET /cases?corporation_id=&kind=&scope=mine|all&before=`：30 条游标列表；`GET /cases/{id}` 返回单据与历史。
- `GET /members?corporation_id=`：具备范围权限的成员选择；`GET /profile?corporation_id=&member=` 读本人或管理员指定成员资格。
- `POST /preview`：管理员发币只读预览，包含成员、金额和原因的指纹。
- `POST /commands`：`configure/profile/apply/resubmit/approve/information/external/reject/cancel/execute/complete/void/grant/reverse`，按动作核对字段、权限和状态。

POST 使用会话、资料门禁、CSRF 和 UUID `request_key`；除预览外写操作带请求键，已有对象更新还带当前版本。ID/版本为十进制字符串，币和 ISK 的 `*_minor` 为整数。相同请求键与内容可重放，换内容或版本冲突返回 409。发币超时须先按同键重试或核对记录，不重新创建发放单。

备份后运行 `npm run db:migrate` 应用 Goose 31 及 River，再启用模块、启动匹配前后端。迁移不插入生效政策、用户资格、PAP 或币。存在福利案件时 Down 被阻止；停用模块不删除历史、不漏掉账号合并。已有福利记录后禁止回退到不参与福利合并的旧程序，需使用兼容恢复版本。本轮没有生产发布。
