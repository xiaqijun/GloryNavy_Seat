## 军团 PAP 与联盟 PAP（来源要求 Goose 44，持久快照 Goose 45）

两类 PAP 分开保存和展示：活动点名、组织者发放产生**军团 PAP**，不设月度达标线，并可按独立配置兑换果壳币；WinterCo 当前月快照属于**联盟 PAP**，按自然人合计，联盟要求默认每人每月 3 PAP。联盟 PAP 在“军团考勤 → 联盟 PAP”子页查看。River 考勤队列每 30 分钟从上游读取完整当前月快照；上游没有增量接口，因此完整读取仍是同步边界，但服务器事务只更新发生变化的行，并在完整读取成功后删除本月已从上游消失的角色。上游失败或不完整时保留上一份快照，不把缺失数据当作 0。联盟 PAP 不自动发放本站积分或果壳币，管理员可在联盟 PAP 子页按月手动兑换，使用独立的 `alliance_pap` 比例并沿用来源幂等与币账审计。

管理员在同一“集结分 → 军团 PAP”页面可打开“统一发放”，集中处理已结束且有有效出勤角色、尚未发放的活动。批量操作仍按活动逐笔调用原发分接口：每场活动保留独立的版本、出勤名单、幂等键、币账和审计；某场失败不会回滚已经成功的其他场次，结果会逐场列出并可刷新后重试。活动详情中的单场发放、更正和撤销入口继续保留，成员不可看到统一发放入口。

联盟 PAP 要求配置仍使用 `GET/POST /api/v1/attendance/pap-requirement`，响应固定带 `source: "alliance"`。`GET /api/v1/attendance/alliance-pap` 返回当前账号合计、同步状态、最近同步时间、版本，以及已映射到该本站账号的角色明细；未绑定角色不展示。管理员在同一页面的联盟 PAP 明细下打开兑换预览，可先通过 `GET /api/v1/attendance/alliance-pap/conversions` 查看仍有未兑换余额的完整月份，再用 `GET/POST /api/v1/attendance/alliance-pap/conversion?month=YYYY-MM` 选择月份结算；省略月份时兼容当前月。联盟与军团比例分别在 exchange 来源设置中配置，已兑换的 0.01 PAP 单位不会重复入账。配置入口在“军团考勤 → 集结分”，仅当前站点管理员可写；POST 使用原 attendance.self 鉴权、宿主 CSRF、乐观版本和审计。范围 1–100000 整数，默认 3。配置只影响联盟 PAP 达标显示，不发放/撤销军团 PAP，也不直接阻断福利。

管理员专用的 `GET /api/v1/attendance/alliance-pap/summary` 为运营面板提供联盟集结满足率：按本站有效绑定的自然人去重，同一账号的多个角色先合计，再与月度目标比较，返回达标人数、有效人数和整数 `rate_bps`。快照未完整同步或同步失败时返回 `available=false`，不把缺失角色计为未达标。

配置变更不重写军团 PAP 流水、不发币/扣币、不限制福利，也不追溯产生惩罚；联盟数据未同步时不显示达标或差额。配置属于全局规则，无账号级余额需要合并；审计保留原操作者。

本地升级需先备份数据库和配置，执行 npm run db:migrate（Goose 45 + River）并重启 API。联盟 PAP 的差量落库不需要新增迁移，旧后端不提供独立子页时前后端需成套回退；保留表和审计，不执行 Down。使用 `WINTERCO_PAP_URL` 与受限的 `WINTERCO_PAP_AUTH_FILE`，无需新增 ESI scope。认证文件优先读取 `read_token`；为兼容现有 seat-pap 文件，也接受 `api_token` 作为回退，令牌只在请求时读取，不进入任务载荷或日志。

## 军团补损关联

军团补损（`srp`）新增出勤关联门槛：同一军团活动中，必须存在同账号、同角色、同击毁报告的已确认损失，且该角色记为出勤。候选或已拒绝的损失、缺席记录、其他账号历史及手填活动编号均不满足。无需活动结束或已发 PAP。PVP补损（`solo`）不要求出勤；联盟补损继续暂停新申请。

组织者在活动损失候选中确认后才生效。宿主注入公开查询及事务锁定服务，按出勤记录的历史账号归属判断；解绑后重新绑定不转移旧出勤，显式账号合并沿用既有归属迁移。不新增 ESI 请求或数据迁移。

Goose 30 [账号合并](account-merge.zh-CN.md)是经过双账号控制验证的独立操作：PAP、出勤和战斗任务当前归属迁入目标，`original_account_id` 保留首次归属；原操作者及审计不改写。完整账号合并保留在线样本，不等于单角色解绑/换绑。

果壳币统一兑换已拆为独立模块，PAP 可配置手动或自动兑币（Goose 26）；详见[兑换指南](exchange.zh-CN.md)。

## 集结分 PAP（Goose 24）

多开叠加已确认：每个有效出勤角色独立计分，再按出勤记录保存的本站账号归属累加。同一活动同一角色最多一份当前积分，重复点名不自动加分。当前按一个活动对应一次集结，默认每角色 1 分，组织者发分时可设 1–10,000 整数分；不新增在线奖励或损失扣分；兑换见独立 exchange 指南。

操作：组织者结束活动后，在“集结分”中填写分值和说明，核对角色数与总分后确认发分。仅给 `present=true` 且有历史本站账号归属的条目发分；新出勤仍须本军团已绑定角色，旧未绑定记录不能发分。活动升级前已有记录不会自动补发；已有有效名单可由组织者明确发分。

活动已经发放集结分后，若管理员在活动结束阶段补录了新的有效出勤角色，活动详情会显示“补发集结分”。补发沿用原活动每角色分值，只处理本活动尚无集结分的新增出勤角色；已有角色不会重复记分或重复兑换果壳币。补发与 PAP 流水、币账、审计在同一事务提交，使用独立幂等键，重复提交不会重复发放。

“更正分值”按目标余额记录差额，“撤销发分”将该活动所有余额归零并保留流水。每次都需要说明、事件版本及 UUID 幂等键。重复同键同内容可重试；不同内容或旧版本拒绝，同值重复发分拒绝，不重复叠加。积分存在时不能重开；先撤销、重开修订名单、结束再发分。活动锁串行化发分与点名/关闭/重开，余额、差额流水、事件版本和审计在同一事务提交，失败全部回滚，无 ESI 请求。

角色解绑/换绑不转移历史账号归属或已发积分。本人可查原归属积分与流水；`corporation.attendance` 管理者可查对应军团并发分，站点管理员沿用现有军团对象策略。普通成员不开放其他账号/军团查询，前端隐藏不替代后端鉴权；宿主仍检查会话、资料门禁和 CSRF。权限目录显示名调整为“军团考勤与集结分”，能力键不变。

新增接口：`GET /api/v1/attendance/pap`（默认本人，`corporation_id` 可选、`period=month|30d`、`page` 从 0 开始，每页 50 条）；管理员集中入口使用 `GET /api/v1/attendance/pap/pending` 获取最多 200 场已结束且有有效出勤角色的待发活动；`GET /api/v1/attendance/events/{id}/pap?after=<cursor>`（50 条流水）；`POST` 同一活动路径执行发分/更正/撤销。精确字段见 [OpenAPI](../../api/openapi.yaml)。活动与角色条目返回 `pap_points`，活动另返回 `pap_issued`。

汇总按活动开始时间划分北京时间本月或最近 30 个自然日，计当前有效余额，不按调整发生日期重复计分；出勤角色人次为角色-活动记录数。同一账号两个角色参加 2 分集结，共 4 分、1 次集结、2 角色人次。分页总分覆盖完整筛选范围，页面逐行显示角色和活动，点击回到出处；尚无排名或任意日期区间；兑换使用独立果壳币余额，历史 PAP 不自动补币。

启用前停止本地 API、备份数据库与配置，运行 `npm run db:migrate` 到 Goose 24（同时 River）并重启同版前后端。无新配置、scope 或后台任务。回退不识别 PAP 的旧应用时先停用 attendance，保留新增表与积分审计，避免旧代码绕过已发分活动的重开保护；不要直接 Down。

## 活动出勤

- 组织者创建活动，使用**本人已绑定角色**读取当时舰队名单。新名单仅保留已绑定本站的目标军团角色，返回跳过总数及外团/本军团未绑定分项；军团归属依据 ESI 可缓存的 affiliation 响应，并非即时组织关系事件。
- 活动开始前不能抓取；活动进行中只允许舰队点名，不提供补录。活动结束后可由管理员补录或修订，补录不向 ESI 请求历史舰队。读取点名来源角色时若 ESI 明确返回已不在舰队/舰队已解散，系统自动结束活动；网络、限流或授权失败不会误判为解散。
- 名单保留每个角色。同一本站账号去重为一人；旧版未绑定记录保留历史含义，新版不新增未绑定出勤。在线不等同于参与活动，不自动认定缺勤、积分或处罚。
- 补录新角色需已绑定本站并确认其所属军团；已有条目的修订使用原记录，即使角色已离团仍可取消误记。修订必须填写原因。后续舰队快照只添加/更新自动记录，不覆盖人工决定，也不把本次不在队的历史出勤自动取消。
- 活动使用版本号；每次写入携带 UUID `request_key`。同一键和相同内容可重试，换内容使用原键、并发旧版本或错误活动状态返回 409。点名/补录/关闭/重开在同一事务保存记录与审计；创建人和创建键保存在活动表。
- 角色首次记入时保存当时的本站账号归属。之后解绑、重新归属、补绑或更改主角色不会转移历史记录；未绑定记录也不自动认领。活动与审计不随角色解绑删除，目前无自动删除期限。

## 在线时长口径

这是**采样估算**，不是 CCP 提供的完整登录会话。仅从启用采集后积累，不能补查过去在线时长，也不使用 `logins` 累计登录次数或 `last_login` 推算整段在线。

1. EVE 模块通过 River 采样当前有效绑定角色；缺 scope 的目标阻塞，授权变化后重新建代。复用现有 SSO 刷新、ESI 缓存、逐笔限流、租约和 fence。
2. 上游 online 的客户端缓存 TTL 为 60 秒；按实际 Cache-Control/Expires 安排下一次请求，并设置最低 60 秒采样间隔。另有现有 1–20 秒抖动和 30 秒派发扫描，队列拥塞、缓存或限流可能继续推迟；不是固定每分钟必达。
3. 只在**真正请求成功**时新增有效样本，包括 304 验证；本地缓存命中不产生新样本。`ValidatedAt` 表示响应验证时间，内容未变化不会使时间停在首次下载；它与 `ContentUpdatedAt` 分开。缓存命中返回已有验证时间和 `Cached=true`。
4. 相邻样本都在线、授权代次相同、间隔不超过 300 秒时，估算这两次观测之间在线。失败写入空值断点，离线、缺失、代次切换或超时段均不跨越累加；最后一次在线样本不外推到当前时间。旧样本在查询时按此规则重新计算，不修改原始观测。
5. 一个本站账号所有符合范围的角色时段取并集。按北京时间 UTC+08:00 切分每日；军团汇总将不同账号时长相加，显示“人时”。当前范围下第一个角色名用作账号显示标签，不声称是主角色。
6. 支持近 7 天、近 30 天。保留 31 天原始样本，给 30 个北京时间自然日及边界样本留余量；每次维护最多清理 10,000 条。暂无长期聚合、月度归档或保留期配置。

无成功样本的日期显示 `—`，不是零时长；有样本但没有可估算在线区间时可显示 0。最近样本失败、超出 300 秒、代次失效或缺授权时，当前状态为未知/需授权，不记离线。有效样本并不保证覆盖整天，样本数可在每日明细查看。派发扫描在每批优先处理 online 目标并扩大批量，避免其他资源的积压持续推迟在线采样；在线 API 仍服从官方缓存与共享限流。

每条样本保存当时有效授权快照中的军团 ID；无有效军团资料记为 0，仍可进入本人统计。军团查询既检查当前绑定/归属范围，也要求区间两端属于该军团；不把加入新军团前的在线历史交给新军团管理者。军团变化有 ESI 资料缓存延迟；不能声称事件级实时精度。

在线样本随 EVE 凭据在解绑时删除；检测到 owner hash 变化也清理旧在线数据，授权更新不跨代次连接区间。在线统计只展示当前有效绑定集合，不把已解绑角色的历史带给新账号。与必须保留原归属的活动账目不同。

## 权限与模块边界

- `attendance` 依赖 `identity`、`eve`、`access`。所有接口受宿主 `attendance.self` 会话、资料完整度和 CSRF 门禁保护，业务对象另行检查。
- `corporation.attendance` 随本功能开放到权限目录，支持军团/联盟过滤。本站管理员、当前有效的 CEO/Director 或明确授权的组织者可管理对应军团活动、查看军团活跃。本站角色不授予任何游戏内权限。
- 普通成员只查看自己的活动条目及本人账号在线数据；管理员可经成员页读取目标成员**仍有效绑定角色**的在线数据，每次查询检查当前管理员标志。管理权限不允许盗用其他成员令牌抓取舰队。
- EVE 网关 `Fleet`、`ActivityProfiles`、`GuardFleet` 和 `OnlineDataTx` 由宿主注入，令牌不出 EVE 模块；身份服务提供批量绑定读取及事务内锁定。活动 SQL 归 attendance 私有 store；在线样本及查询归 eve 私有 store。
- 网络抓取在事务外完成，写入前重新检查管理权限，再按已排序的角色锁 → EVE 凭据 → 活动顺序提交，校验来源角色当前归属、授权代次及活动版本。数据库事务不包含网络或等待另一个池连接的跨模块查询。
- 活动详情保留历史账号归属，因此普通用户仍能读取原属于自己账号的活动记录；这不扩大解绑角色的在线/合同读取权。

| POST /universe/names | 公开 | 遵守实际响应头 | 按官方目录/实际响应观测 |

两项 scope 已在既有 57 项授权清单中，无需扩大请求清单；旧角色可能仍需重新授权。舰队是否允许读取以 ESI 实际响应为准，403、无舰队、网络失败均不创建虚假出勤。Goose 22 开始按每次点名保存舰船、星系和入队时间；姓名来自 ESI，SDE 不提供角色姓名或在线历史。

## 启用、升级与回退

1. 备份数据库和 `.env`，停止旧服务，使用 `npm run db:migrate` 维护 Goose/River 两条迁移线；当前应用 Goose **29**，包含 21–26 的出勤、战斗证据、星系名称、PAP 与兑换结构，不采用草稿 SQL。已在 29 的生产启用模块不新增迁移。
2. 在原 `MODULES` 中追加 `attendance`，保留原有模块；默认清单为 `system,identity,eve,access,community,attendance`。同版后端与前端一起发布后重启。
3. 启动后派发器为现有凭据建立 online 目标；缺 scope 的角色明确阻塞。新授权代次下次派发恢复，不在迁移里填造历史样本。
4. `/attendance` 提供活动，`/attendance?view=online` 提供在线图表；`/sync` 的“在线状态”资源继续查看任务、失败原因与下一次运行。
5. 停用新版本的 attendance 后不再新增在线任务，在途任务处理器暂停一小时并等待重新启用。表不删除，其他 ESI 资源继续工作。

**回退到不认识 online 资源的旧二进制**：停服务，取消 `eve.character-online.v1` 的非终态 River 作业，将 online 同步目标设为 `blocked` / `module_disabled`，清除 active job/lease 并递增 fence；恢复旧 `MODULES` 和旧发布目录后启动。保留 Goose 21 表以免丢考勤；不要直接运行 Down。否则旧派发器会遇到未知资源。再次升级会恢复 `module_disabled` 目标。数据库完整恢复仅用于确认过的数据回滚，不作为普通代码回退步骤。

## 验证边界

当前舰船与损失扩展使用 Goose 22；其新增验证与本地启用状态见项目状态。

数据库与 HTTP 夹具覆盖多角色去重、外团过滤、手工优先、幂等、并发版本、授权代次、管理员撤权、单连接池、采样失败/间隔/军团边界。浏览器夹具覆盖创建、点名、补录、图表/每日表、未知和零值、桌面与 375/320px。生产真实采样和真实舰队点名是否完成，以[项目状态](../project-status.md)的本次记录为准；不把夹具截图当作真实军团活动。

## 舰船、装配与损失（Goose 22）

展示修正：活动详情的成员条目增加 `solar_system_id`、`location_observed_at`，来自该角色最新观测时间的舰船快照；没有有效星系时均为 null。名单直接显示点名星系与时间，舰船/损失摘要显示各自位置，不以个人当前位置回填。只是读取和展示已有数据，无新迁移。

- 每次点名生成独立舰船快照，保留船型、星系、入队时间和名单响应验证时间。重复请求不重复记录，换船与再次点名不覆盖原快照。新补录角色也必须已绑定本站。
- 后台使用每个参战角色自己的 `esi-location.read_ship_type.v1`、`esi-assets.read_assets.v1` 取得当前船只唯一 ID，读取全部资产分页，将 `location_id` 等于该船 ID 的装备、无人机和货舱物品关联到快照。考勤不保存其他船只的资产；共享私有 ESI 缓存仍加密、按角色与授权代次隔离。只关联直接子项，暂不展开资产容器，不提供模块在线状态及深渊装备实际属性。
- 当前舰船 TTL 5 秒、资产 TTL 3600 秒，实际响应头优先。保存舰船验证时间、最早资产分页验证时间及内容时间，不把缓存装配宣称为点名瞬间的配置。采集前后核对船只 ID/船型；开始采集距点名超过 3 分钟、已换船或资产缺失时明确标记，不补造历史。相同船型在第一次私有采集前已换船仍无法由舰队接口识别；接口不提供原子快照。
- 资产最多 100 页，页数改变或数据不完整不发布。网络预算 55 秒，临时错误重试复用缓存；5 次失败后标记失败。旧点名过期不能刷新成新装配，需再次点名形成新快照。
- 损失使用个人 `/characters/{character_id}/killmails/recent` 与公开 `/killmails/{killmail_id}/{killmail_hash}`，只保留 victim 为参战角色且位于活动时间窗内的报告。个人授权覆盖本人的损失，不需要军团职务。官方列表回溯 90 天，不能把含击杀的每一项都算作损失，也不承诺补查更久的报告。
- 结束活动保存结束时间，重新开启清除结束时间。每轮扫描固定截止时间，按页持久推进，完整轮次后遵守列表缓存且至少间隔 5 分钟。结束后继续扫描 24 小时以容纳延迟报告，之后可手动重试。
- 击毁报告没有活动 ID，匹配项一律先作为候选。组织者填写原因确认或排除；同一报告只能被一个活动确认，后续同步不覆盖人工决定。使用版本号和幂等键，跨活动重复确认返回 409。保存船型、时间、星系、位置旗标、嵌套物品及毁坏/掉落数量；缺物品明细不代表零损失。暂未增加 ISK 估价或 SRP 发放。
- 船型、装备与星系名称统一走 SDE 中文优先；缺失名称回退 ID，损失数值位置旗标保留 ID，不猜名称。GET 只读本地数据，详情显示最近 20 次舰船快照、100 条损失，超限提示截取，原数据保留。
- `attendance.battle.v1` 与 `attendance.dispatch.v1` 接入共享 River，独立 attendance 队列并发 2，扫描周期 30 秒。事务内保存持久任务，队列只含任务 ID。发布重查 90 秒租约/fence、原账号、owner hash 和授权代次，依次锁身份、凭据、活动、任务；网络在事务外。解绑或换绑后不向旧考勤继续采集，已保存证据保留原活动归属。普通成员只读自己的历史证据，管理者读取授权活动范围。
- 缺授权、失败和未检查分别展示；更新授权后可在损失区重试，仍遵守缓存与预算。没有开放成员全部资产浏览权限。

新增接口位于 `/api/v1/attendance`：GET `/events/{id}/characters/{character_id}/battle`；POST 同路径加 `/refresh`；POST `/events/{id}/losses/{loss_id}/review`。管理写沿用 `corporation.attendance`、CSRF 和对象检查。
