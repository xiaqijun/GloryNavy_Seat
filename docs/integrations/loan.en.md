# Loan module

## 2026-10-17: Loan officer operating permissions

A loan officer is a site account with `corporation.loan`. Permission management offers a named role preset that must be saved and assigned/revoked for members; administrators can open configuration from loan settings. Configured corporations, current account membership and object checks still apply. This role grants neither site administration nor permission management. Choosing a contract character does not automatically grant loan permissions to its owner.

Game character configuration is separately labelled “Set contract character”, and loan details/contribution instructions use “Contract character” instead of the former “Current loan officer” label. Existing custodian_character_id/name, the `/settings/custodian` endpoint and active-binding checks are retained. No backend, migration or contract workflow change.


## Automatic excess security and 80% collateral (2026-10-16, Goose 89)

Required security = max(0, principal − max(0, personal limit − existing responsibility)). The automatic amount is max(0, required security − this case's effective coverage − pending allocations). Effective coverage includes accepted/active guarantees and approved/held collateral. Pending allocations include invited guarantees, proposed collateral and frozen awaiting-delivery targets; they prevent duplicate allocation but never approve a loan or reserve guarantor credit. New invitations/selections require fresh active borrower credit. Transactions lock account credit before the case, then recalculate the amount. A zero gap rejects creation; security is not shared between cases.

- Submitted/awaiting_acceptance case details add `security`: `credit_ready`, `available_credit_minor`, `required_minor`, `effective_minor`, `pending_minor`, `unallocated_minor`, `legacy_pending`. Amounts are integer minor units. With unavailable credit, `credit_ready=false`; zero values do not establish approval eligibility.
- Invitation `amount_minor` may be omitted or zero for automatic calculation. A positive value is an expected amount and must exactly match, otherwise 409. Guarantees support 0.01 ISK while retaining guarantor-capacity and principal-share limits. Acceptance rechecks guarantor credit and rejects an obsolete amount exceeding the remaining gap when fresh active borrower credit exists. Legacy invitations without valid borrower snapshots remain compatible, but loan approval still requires fresh active credit. Rejected/released invitations are retained and may be followed by a new invitation; each case/account permits only one record outside those two states.
- `POST /api/v1/loan/cases/{id}/collateral-quote` accepts the same `character_id/items` selection as saving. It requires the borrower, a currently bound character, a pending case, session, `loan.self` and CSRF. Returns `security`, `valuation_minor`, `covered_minor`, `required_minor`, `shortfall_minor`, `can_submit`. Values come from authoritative assets and market averages, never client prices. Network reads occur outside write transactions; every selected item must have a valid price.
- Eligible collateral = floor(total selected value × 8000 / 10000), rounded down to 0.01 ISK. It must be at least the automatic target; equality is accepted. Saving optionally accepts expected `coverage_minor`; a nonzero mismatch is 409. Saving revalues and rechecks the gap and quantities, then freezes `coverage_minor` and `valuation_minor` without granting effective coverage. For 10B available credit and a 12B loan, the target is 2B and items must total at least 2.5B.
- Completed-contract delivery revalues the exact items. If 80% is below the frozen target, `loan_collateral_value_insufficient` leaves the request and contract claim unchanged. Success records the frozen coverage target even when item value is greater; approval by another manager is still required. New collateral uses fixed 8000 bps; client `haircut_bps/valuation_minor/covered_minor` do not control it. Legacy `collateral_cap_bps` remains for API/data compatibility without an extra multiplier on new collateral. Direct registration without `request_id` remains callable but requires a pending case, a current gap and sufficient value at 80%.
- Pre-Goose-89 requests retain zero target/value and the old pool haircut at delivery; finish or cancel them before allocating new security. Existing registered collateral is not recalculated. Goose 89 Down refuses nonzero targets or repeated case/account invitation history. After new records exist, do not run an older program that ignores targets/history; deploy frontend and backend together.

Missing valuation returns `loan_collateral_quote_unavailable` (409), insufficient value `loan_collateral_value_insufficient` (409), and no new gap `loan_security_not_needed` (409). Changed expected amounts, versions, states or quantities use the existing conflict error. Cancelling a pending request releases its allocation while retaining records/audit. Real game delivery acceptance remains pending.

Guarantor details (2026-10-16): `GET /api/v1/loan/cases/{id}` adds optional `guarantor_character_name` to `guarantees[]`. After existing case-object authorization, the host-injected `CharacterNames` resolves positive stored character IDs in one deduplicated batch, independently of the invitation candidate directory. Ownership and decision audits remain unchanged. Empty names, a missing resolver or lookup errors omit the name while preserving all records and IDs; an empty list remains `[]`. The UI displays each guarantor, exact amount and state, falling back from name to character ID and then the legacy guarantor account. Only the detail response gains this display field; creation/decision responses are unchanged. No migration.

Loan detail identities added on 2026-10-16: show the case's `pool_name` as the lender, falling back to the matching pool context name or pool ID, with a shared-pool marker where applicable. Show the pool's current `custodian_character_name` as the current loan officer, falling back to the character ID; distinguish an unconfigured officer from unavailable pool context. Shared-pool contributions are not allocated from an individual contributor to each case. The current officer is not evidence of the original contributor or historical disbursement character. This uses existing authorized context/detail responses, with no API or migration change.

## One personal limit (2026-10-16)

The single visible and actionable personal limit is `total_limit_minor` from the latest valid evaluation. Income, consumption, score and asset calculations stay unchanged. `unsecured_limit_minor`, `asset_support_limit_minor` and other legacy components remain historical evidence and API compatibility fields, not separate approval thresholds. Existing snapshots are not rewritten.

Remaining credit = max(0, personal limit − existing responsibility). Required security = max(0, new principal − remaining credit). Existing responsibility retains full principal for approved/funding/active/defaulted loans plus accepted/active guarantees given to other borrowers. Settlement or cancellation releases it; partial repayment does not release partial principal capacity. With 10B remaining, a 12B application needs 2B of coverage. Accepted/active guarantees and approved/held collateral for this case can be combined. Invitations, pending deliveries, unapproved collateral and other cases' security do not count. A fresh active zero limit permits fully secured borrowing, but missing, stale or suspended credit still blocks approval.

`POST /api/v1/loan/cases/{id}/review` retains management scope, non-self review, state and version checks. Approval guards the active account against merging, takes sorted module-private account credit locks, then the shared-pool and case row locks, and rereads credit, responsibility, available cash and coverage. Guarantee acceptance locks both guarantor and borrower credit, rereads the snapshot, and remains limited by the guarantor's unused personal capacity. Approval, its immutable evaluation and `credit_coverage_checked` audit commit atomically. The audit records `model=single-credit-v1`, personal limit, existing responsibility, principal, required coverage and accepted coverage. No migration; Goose remains 88. Deploy frontend and backend together. Rolling back the approval code restores the old dual thresholds; do not retroactively reinterpret new approvals using the old rules.

2026-10-16 personal asset collateral (Goose 88): borrowers first select assets of a currently bound personal character, save an awaiting-delivery record in `loan_collateral_requests`, then deliver through an in-game personal item exchange contract. The host injects candidates through the EVE asset and SDE naming services, preserving credential/fence checks without importing private stores across modules. Only hangar roots are offered; fittings and container contents travel together, and blueprint copies are excluded. Each request accepts at most 100 roots / 500 expanded items at one location. Saving re-reads the authoritative snapshot and serializes account, case and character-asset reservations. Pending records freeze source, recipient, items and snapshot time and freeze valuation/target under the Goose 89 rules above, but grant no effective coverage.

- `GET /api/v1/loan/cases/{id}/collateral-assets?character_id=...`: only the borrower may read assets of their bound character; management rights do not grant selection rights. Returns quantities, available quantities and contents.
- `POST /api/v1/loan/cases/{id}/collateral-requests`: body `{"character_id":"111","items":[{"item_id":"501","quantity":"3"}]}` (local example IDs). Only submitted/awaiting_acceptance cases accept new requests. Returns an LNC reference in awaiting_delivery state.
- `POST /api/v1/loan/collateral-requests/{id}/cancel`: body `{"version":1}`; only the borrower can cancel an unregistered delivery. Changed versions or delivered records return 409. Withdrawing an application cancels pending requests and releases selection quantities in the same audited transaction.
- Existing collateral registration accepts optional string `request_id`; the new UI always supplies it. Require a personal contract from the frozen source to the frozen, still-configured custodian, completion after request creation, complete cached items, zero price and reward, and an exact type/quantity multiset with no requested/extra items or blueprint copies. Inside the transaction recheck current binding, contract cache, state and version, acquire the permanent global contract claim, create proposed collateral, mark the request delivered and audit atomically. A manager other than the borrower must approve before coverage counts. Legacy completed-contract registration remains compatible.

Case details include `collateral_requests` under existing read authorization. Requests follow case ownership during account merging; merge previews count them and cases retain their first original account. Cancellation, rejection and settlement do not delete delivery evidence, release historical contract claims or return in-game items. Once requests exist, do not downgrade to a program that ignores them; Goose 88 Down refuses to drop a nonempty table. Real personal asset and in-game delivery acceptance remains pending. Collateral linking is an explicit member action after contract synchronization, not an automatic scan.

The 640px detail dialog groups exact principal, interest and total due, repayment terms/installments, item collateral and existing personal guarantees. The primary action selects items; guarantor invitations remain secondary. The searchable asset picker shows quantities, locations, snapshot time and bundled contents. Saved requests show the delivery characters, copyable description and complete item list, with actions to link a completed contract or cancel the pending selection. English and Chinese layouts retain 44px controls and collapse on narrow screens.

Application withdrawal added on 2026-10-16: `POST /api/v1/loan/cases/{id}/cancel` accepts `{"version":1}`. Only the current borrower can withdraw a `submitted` case; administrator privileges do not permit withdrawal on someone else's behalf. Invalid input returns 400, non-owner access 403, and state/version conflicts (including retries) 409. Session and CSRF protections remain enforced by the host. One transaction guards the active account, locks and rechecks the case, marks it cancelled, releases invited/accepted/active guarantees and proposed/approved/held collateral with incremented versions, and writes an `application_cancelled` audit. Any failure rolls back everything. New guarantees/collateral also lock and recheck the case before insertion, preventing late writes after withdrawal. Reviewed or funded cases cannot use this endpoint. Cash/payment ledgers, retained records and immutable contract claims are unchanged. Releasing capacity does not return game items; arrange collateral returns separately with the manager. The approval center projects the case into history and stale review actions are rejected by version checks. No new migration.

Loan and contribution forms use shorter options and grouped fields, with interest details available on demand. Mobile records expose both details and withdrawal actions. Chinese and English remain supported.

Repayment choices added on 2026-10-16: single payment after a 1–365 day term (30/90/180/365 day presets), single payment on a selected date, or installments. Relative terms still start at verified disbursement; installments retain 1/3/7/14/30 day intervals. A fixed date uses `repayment_date=YYYY-MM-DD`, one installment, and an omitted or zero interval. Select tomorrow through 365 days ahead in Beijing time, due at 23:59:59 that day. Goose 87 stores `requested_due_at`; `first_due_at` remains empty until funding. The annual rate is frozen at application. Dated interest is initially quoted from the application calendar date to maturity, then finalized from the verified contract completion date using Beijing calendar-day differences (minimum one day), never exceeding the estimate. Final amounts and schedule are audited. Completion must be at or after application, no later than verification, and before the deadline. Late synchronization does not extend maturity. Other loans keep their original interest snapshot. Once dated loans exist, do not roll back to a binary that ignores the deadline; the Down migration refuses to discard it.

The 2026-10-16 submission fix keeps character IDs as `int64` between the service and private store and explicitly types amount addition as SQL `bigint`, avoiding driver encoding and PostgreSQL parameter inference errors. HTTP field formats are unchanged and no migration is required. Submitting an application saves its review record and interest snapshot; it does not set repayment dates, disburse funds, or increase pool cash.

Status: The shared pool is published. Loans use game ISK. There is one fixed shared pool: personal or corporation contributors submit amounts to it, and the borrower is a site member account. All characters bound to one account share its loan responsibility.

Interest follows a familiar loan mechanism: a manager configures an annual nominal rate in basis points (100 bps = 1%), and each application calculates fixed simple interest once as `principal × annual rate × installment count × interval days ÷ (10000 × 365)`, rounded once to ISK minor units. Principal and interest are stored separately and split across equal installments; the final installment absorbs rounding. The annual rate is snapshotted with the application, so policy changes never recalculate existing loans; dated interest is finalized at funding as described above. Loan payments accept exact 0.01 ISK amounts so fractional interest can be settled. Contributions and administrator funding still require whole ISK; automatic guarantees support 0.01 ISK. A normal contribution is pending until the contributor sends a completed cash-only contract to the configured personal custodian character. The amount, direction, acceptor and empty item set are checked and the global contract claim succeeds before the amount becomes pool cash. A site administrator may also register pool capital directly; that entry is written to the loan ledger and does not create or verify an in-game contract. Approval is not disbursement; disbursement also reserves and debits available pool cash after contract verification.

The system evaluates the credit score, personal limit, and rule version from loan evidence; administrators cannot edit these values. Personal base credit also reads verified personal-wallet snapshots for the account's active bound characters and keeps income capacity and consumption capacity as separate positive signals; it never subtracts them into net income. Each signal is measured with the configured income/consumption ratio and term, then combined with the configurable income weight (70% by default) and consumption weight (30% by default). There is no personal hard cap. Too few samples, stale data, unavailable data, or no valid income and consumption observations are treated as insufficient wallet evidence; the default is to suspend personal credit, while managers can explicitly switch this to the legacy verified-pool fallback. Wallet authorization only controls evidence availability and is never a score input. The final application remains limited by shared-pool available cash. `system-v2` weights repayment at 55, leverage at 20, guarantee/collateral history at 10, PAP score at 5, and asset-scale score at 10. Authorization state and account age are never score factors. PAP is split into two factors: the closed-event corporation activity attendance rate over the last year (3 points) and the share of complete alliance PAP snapshots in the last six months that meet the configured monthly requirement (2 points). Each factor is proportionally rounded and capped. Missing activity records, missing alliance snapshots, or incomplete syncs remain neutral rather than becoming a zero-score penalty. Asset-scale scoring is enabled: the service reads personal `esi-assets.read_assets.v1` holdings for every active character bound to the account and values the aggregate with EVE's global average-price table; corporation assets and wallet balances are excluded. The total is scored as 0 below 100 million ISK, then 2, 4, 6, 8, and 10 points at 100 million, 500 million, 1 billion, 5 billion, and 10 billion ISK. Holdings without a valid ESI average price are skipped while other priced personal holdings continue to count; a partial character read is retained with an evidence error, and no priced holdings leaves the asset factor neutral. The evidence retains its observation time, snapshot identifier, and unpriced type count. Authorization only controls whether evidence can be read or refreshed. Complete personal asset value also contributes to the same personal limit under the configured asset LTV, default 1000 bps (10%). A periodic backend job evaluates credit every 24 hours and stores a snapshot; pages, guarantees, collateral, and approvals only use the newest snapshot, and missing or stale snapshots block new credit actions. A default suspends the credit state. The personal-limit calculation uses the shared pool's verified cash balance as its principal-pool base and is recalculated from the current score; unverified contribution promises and website balances are excluded. Each approval records an immutable evaluation snapshot. Guarantee and collateral coverage are rechecked in the approval transaction. A guarantee amount is limited by both the configured share of the loan principal and the guarantor's current available total-responsibility capacity. Acceptance rechecks the total responsibility remainder in a transaction before reserving it. Collateral remains pending until an administrator approves a completed item-exchange contract whose item snapshot is read and frozen by the server; it is released when the loan settles. The module never auto-debits wallets, liquidates collateral, or treats a wallet balance as payment evidence.

The shared pool is a fixed singleton. The module migration creates one open corporation pool from the corporation with the largest known character profile set; the page does not expose pool creation, switching, or pool limit configuration, and members submit amounts only. A loan manager selects an actively bound personal EVE character as the contract officer. Incoming, disbursement, and repayment contracts use that officer as the receiving character, and the service rejects self-delivery by the same character. A site administrator can register pool capital directly; the entry is auditable and does not depend on an EVE contract. Verified contract entries and administrator ledger entries are the sources of lendable cash; a wallet snapshot is never treated as payment evidence. No contract verification is allowed without a valid officer. Unverified promises and website balances are never treated as cash. New collateral covers the frozen gap and cannot exceed 80% of actual item value; legacy compatibility follows the Goose 89 rules above.

Loan management is assigned through the site's permission roles; selecting an EVE contract officer does not grant loan management access. The account must first receive `corporation.loan`, then an authorized manager can select its actively bound personal EVE character.

Payment verification uses the existing EVE contract cache service. Disbursement requires a finished contract, exact amount, and the borrower receiving character. Repayment may be partial and is allocated from the earliest unpaid installment while preserving principal and interest detail. One in-game contract can be claimed by only one delivery module; retries do not credit twice.

The module exposes the authenticated `loan.self` routes described in the Chinese guide, including contribution submission and automatic verification against recent synchronized finished contracts. `GET /api/v1/loan/guarantees/candidates` returns selectable active character names; invitation creation resolves the account again. Corporation contributions and custody configuration additionally check `corporation.loan`. Goose migrations 71–73 and 79–82 add the shared-pool contribution, cash ledger, credit evaluation tables, rate snapshots, and the fixed shared-pool seed. The page appears when `loan` is enabled in `MODULES`.

The policy endpoints are `GET/POST /api/v1/loan/settings/policy` and `GET /api/v1/loan/evaluations`. Policy writes are versioned and manager-only; evaluation history is scoped to the current account.

Pending corporation-pool applications are also exposed as the `loan` source in the approval center. The center is read-only and reuses this module's review endpoint; personal lender decisions stay on the loan page.

The loan module uses two navigation pages: `/loans` is the Loan dashboard and shows the shared-pool overview; `/loans/operations` is Loan operations and contains applications, contributions, guarantees, collateral, and loan records, with Loan dashboard, Loan operations, Risk settings, and Evaluation history tabs. Beneath the tab switcher, the Loan operations tab shows only the caller's credit score and personal limit; score factors are not displayed. Risk settings is manager-only and configures the annual rate, income window, debt ratio, term, score factor, asset LTV, sample threshold, evidence freshness, the guarantee cap and fixed 80% collateral ratio, direct administrator funding, and contract officer. Evaluation history shows the caller's immutable periodic and approval snapshots with a single personal-limit column. Loan settings are visible only to loan managers, who can select the officer from all active bound EVE characters rather than only their own account. Administrators can register pool capital directly from this page; the entry is written to the loan ledger without creating or verifying a game contract. Contributions are shown as compact list rows with lender character, contribution type, amount and state; clicking a row opens its detail modal. A pending detail shows only the copyable fields needed to create the contract: the loan officer character name, payment amount and contract note. The character ID remains in the API and backend for validation; the page falls back to the ID only when the name is temporarily unavailable. The contract type and no-item requirement are explanatory text. After synchronization, the system automatically verifies a matching finished contract; the page provides no verification button. Lender and receiving characters are selected by nickname from the current account's bound-character dropdown; the submitted character ID is supplied by the system. Installment applications offer intervals of 1, 3, 7, 14, or 30 days. Single-payment terms and dates follow the rules at the top of this guide. The first repayment date is generated after verified disbursement as disbursement time plus the selected interval, then remaining installments use the same interval. Guarantee invitations use a selectable active character list. Collateral starts with personal asset selection, then links a completed item-exchange contract from the saved delivery record; the automatic target must fit 80% of the item value before saving and again at delivery, and coverage takes effect only after approval. The operations page shows only the system credit score and personal limit; score factors are not displayed. Asset-scale scoring uses the complete personal ESI snapshot described above; wallet balances are not a substitute and incomplete asset evidence remains neutral. Corporation contributions require the corporation permission. Approval reads the newest credit snapshot and rechecks cash, guarantees, and collateral before accepting an application; a stale or missing snapshot blocks approval. The Loan business dashboard links clearly to operations; the operations page always shows a “My guarantee invitations” section, where a guarantor can review the loan principal and guarantee amount, then accept or reject an invitation. Acceptance rechecks the current total responsibility capacity.
