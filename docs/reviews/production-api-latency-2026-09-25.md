# 生产页面数据加载排查（2026-09-25）

用户反馈登录后各页面首次读取偏慢。本轮只读检查公网机安全访问日志、应用机 HTTP 路由日志、两机负载，并从同一台本机分别请求 EdgeOne 域名与公网源站。生产配置、DNS、业务数据未改。样本较少，且本轮没有真实管理员浏览器会话的完整瀑布图；以下结果用于定位，不是全体玩家的 SLA。

| 链路 / 接口 | 样本 | 观察 |
| --- | ---: | --- |
| 本机经 EdgeOne 请求极小的匿名 `login-status`，每次新连接 | 8 | 总耗时中位数约 1.36 秒，P95 约 1.50 秒 |
| 同机 `--resolve` 直连公网机，同域名、证书和路径 | 8 | 中位数约 0.24 秒；有一次约 1.38 秒的网络抖动 |
| 同一连接连续请求，排除反复握手 | 各 5 | EdgeOne 后续约 0.49–0.54 秒，直连后续约 0.08–0.09 秒 |
| 公网机本地经站点反代请求同接口 | 1 | 约 0.07 秒；应用机日志中该路由处理约 0 毫秒 |
| 生产浏览器经 EdgeOne 连续请求同接口 | 6 | 首次约 1.1–1.7 秒，后续约 0.48–0.60 秒，HTTP/2；无法在该浏览器成功绕过 EdgeOne，不能把浏览器“直连”数据当作对照 |
| 公网机审批列表 `/api/v1/approval/items` | 16 | 平均约 0.46 秒，P95 约 0.69 秒；应用机同路由 14 次平均约 0.38 秒 |
| 公开活动 `/api/v1/eve/public/activity` | 6 | 公网机平均约 3.44 秒，最长约 6.27 秒；该接口刷新时会等待外部战绩与在线来源，与成员页延迟是独立问题 |

域名当前 CNAME 指向 EdgeOne，动态 API 响应带 `Cache-Control: no-store` 与 `EO-Cache-Status: MISS`。大多数已登录业务接口在应用机为几十毫秒，但首次进入页面通常还要经过会话、模块/权限、页面上下文及列表的顺序请求；每轮额外网络等待会累加。应用机约 16 vCPU、15 GiB 内存，检查时系统负载约 2、可用内存约 12 GiB；公网机也未见 CPU 饱和。因此不能把普遍的首次读取慢归因于 1Panel 静态站点、单纯前端渲染或服务器内存不足。

优先核对 EdgeOne 控制台中此域名的“智能加速”当前状态与套餐，再做开启前后同机、同路径、冷/热连接 A/B。腾讯云[站点加速说明](https://cloud.tencent.com/document/product/1552/96193)称智能加速默认关闭；[规则引擎说明](https://intl.cloud.tencent.com/zh/document/product/1145/54759)列出智能加速动态路由与其匹配条件。当前状态尚未取得，不能据默认值断定本站一定关闭；[计费说明](https://cloud.tencent.com/document/product/1552/104319)也提示智能加速会影响计费口径。保持 `/api/` 私有数据不缓存，不为缩短等待而放宽 Cookie、鉴权或 CORS。

若智能加速已开启或试验后仍慢，再比较不同 EdgeOne 节点、用户地区与源站直连；必要时评估同域名 DNS 直连方案对 HTTPS、静态资源、防护和不同地区用户的影响，不能只凭本机一次直连样本切 DNS。另对审批列表 0.3–0.6 秒的应用耗时及公开活动 3–6 秒的外部刷新分别分析，避免把独立瓶颈掩盖在网络统计中。最终应以真实授权会话记录各页面请求链和可见数据时间，并在调整后复测。
