# 反馈完整流程

用户先指出奖励配置按钮位置及状态办理不清楚，随后明确要求完整流程，并选择“完成后由提交人确认，可退回继续处理”。此前仅排版的方案未单独发布，本轮一起交付。

提交 → 管理员采纳/不采纳 → 开始处理 → 提交完成 → 提交人确认。待确认可由拥有者说明原因退回，完成可重开、关闭可重提；管理员不能代确认或办理本人反馈。通过原 messages API 的锁、版本和幂等检查合法跳转；普通回复不改变状态。首次采纳发币规则及冻结额沿用 Goose 104，不在重试、退回、重开、迁移或账号合并时重复发币。Goose 105 仅扩展状态约束，不自动更改历史 resolved 或现有奖励配置。

详情将当前进度和可操作按钮放在历史回复前；每个操作展开说明后确认，必填原因与结果由前后端共同检查。页头提交和奖励设置右对齐，手机单独换行。按原语言词表复用已有英文，新增固定文案同步翻译。退回、重开和重提使用稳定状态消息 ID 作为独立待办提醒引用，普通回复不新增该事件，不自动启用提醒类型。

GitNexus upstream 的核心 Reply/statusOK、前端 Workspace/Thread 与私有提醒查询为 LOW。新组件/验证器尚未入索引，按源码核对调用关系；测试入口由框架调用，未解析不等于无影响。提交前 detect_changes 为 HIGH，28 个文件与 6 条来源于反馈回复事务的流程，已提示用户并核对没有其他业务权限或币账改写。

隔离 PostgreSQL 的 6 项反馈流程/奖励/隐私 race 检查通过，包含确认、退回、多次往返、并发版本冲突、不能自审/代确认、必填原因、币账仅一笔；宿主 4 项反馈权限/CSRF/截图/停用合并回归通过。2 项退回/重开/重提提醒稳定引用测试及最后私有查询的 vet 通过。TypeScript、构建及定向 lint 通过，保留原 screenshots.tsx Fast Refresh 提示。20 项中英文桌面/375px 浏览器检查通过；最后补齐忙碌锁定后，最终构建另复测 4 项完整流程。页面使用模拟会话，真实身份和事务权限另由隔离数据库测试覆盖；真实双账号与游戏邮件验收见 FEEDBACK-FLOW-01。

初次本地检查发现词表处理未覆盖原有非字符串属性名，修正为从 HEAD 原字节及 TypeScript AST 构造增量词表，没有发布损坏词表。首轮 4 项英文断言使用了与原词表不同的表达，改为现有英文后复测通过。

原有并发回复回归改用合法的采纳步骤，避免继续假定管理员可跳过提交人确认直接 resolved；与提交限额/重复提交 2 项 race 检查另行复核。

发布待完成，迁移后不回退到不识别确认历史的旧前后端。
