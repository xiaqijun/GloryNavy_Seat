# 预警累计取整修复（2026-10-24）

## 范围与状态

后端与 Goose 106 已实现并完成定向隔离 PostgreSQL 验证，尚未发布。修复新的 client-usage 分段累计多扣；Sentry 端旧索引升级由其主仓单独修复。部署前后都保留现有价格、开关、游标、历史余额及全部账目，不按故障经过时间或监控奖励推算补扣。历史问题证据保留于[10 月 20 日核查](sentry-billing-audit-20261020.md)。

## 行为与边界

- 新消费逐原始 usage ID 原子提交：grant、charge、正金额币账、累计取整余量同事务；每账号钱包锁串行化并先核对活跃账号。
- 余量键为账号＋星系＋价格版本＋冻结 unit_seconds／unit_price_minor，保存已付小数部分；每段费用为累计向上取整的差额。旧预付 grant 接口仍按其冻结合同处理。
- 0 分区间仍保存 settled 证据，grant 直接完成，不写 0 值币流水。核验规则是每个正金额新 grant 恰有一条匹配 `alert_reserve`，0 分 grant 没有币流水。
- 失败不推进余量；重复使用原冻结记录，不随当前价格重算。不同页面大小仍使用原始身份。旧非累计的已结算区间完整覆盖重放证据时跳过，部分重叠拒绝，不猜测未结算部分。
- 迁移不从旧金额建立余量；新桶从 0 开始。账号合并将已付余量相加（允许超过 1 分），只抵扣后续费用；原账归属不变，合并预览指纹包含余量。
- OpenAPI 消费 `coins_minor` 下限改为 0，前端响应校验同步接受 0 并继续拒绝负数、小数和不安全整数；无 HTTP 路由、认证或 Sentry wire 字段变化。

## 本轮证据

在独立 PostgreSQL 18.6 容器与测试数据库的随机 schema 上验证，没有向生产账库插入测试消费或余额。

- 原实现基线：60 个 1 秒区间、200 分/小时，实际 60 分，回归期望 4 分，明确失败。
- 修复后 8 项费用回归通过：合计 4 分、0 分消费、不同账号／星系／版本／费率、重启与重复、并发重复、余额不足、币账故障全事务回滚、旧合并批次重放、账号合并余量与原归属、退休账号拒绝、整数溢出。
- 迁移回归通过：从 Goose 105 的旧账升级 106，旧 grant／charge／ledger 内容哈希一致；重复 Up 无变化、初始桶为空、产生新证据后 Down 拒绝。
- worker 回归通过：分页中途失败游标不前进，重启后不同页大小仍使用相同原始 usage ID 及幂等键。
- 最终后端定向 `go test -race` 20 项全部通过，覆盖 exchange、sentry、宿主 app 的费用、预付兼容、价格及 HTTP 权限；三包 `go vet` 通过。前端回归先在旧校验复现 0 分响应拒绝，修改后 Sentry 7 项单测、TypeScript 构建检查及修改文件 lint 通过；Vite 生产构建与公共首页预渲染成功。
- GitNexus 已对修改的旧方法运行 upstream impact。账号合并 store 为 LOW（1 个直接调用方）；River worker 和结算方法调用图未解析，已人工追踪宿主与 worker。完整索引刷新因 worker 启动超时失败，图不作为独立的完整影响证明。
- `detect_changes --scope all` 报告已跟踪 12 文件、16 符号、5 个结算相关流程，风险 medium；新增文件和旧索引的行号偏移另以实际 diff 核对，不将其当作完整新图。

## 发布和回退

先发布兼容 0 分响应的前端（兼容旧后端），再发布 SeAT Goose 106 与匹配后端，最后恢复 Sentry 证据写入，避免恢复后仍用旧逐段取整。按[部署流程](../deployment.md)从干净、已推送的 main 构建带校验和的发布包；激活前备份数据库和环境，停止旧 API/worker，执行 Goose/River 迁移，启动匹配后端并检查就绪、版本、迁移与真实消费链路。前端只变更响应校验，无布局或样式变化；不得重置 reconcile 游标或自动回填故障期。

新桶为空且没有 cumulative grant 时允许 106 Down；一旦有新数据，Down 显式拒绝。产生新账后禁止运行忽略余量、零金额或合并参与方的旧程序，应保留 schema 与全部新账向前修复。若紧急暂停收费，使用原管理员开关及同步流程，不能用旧备份覆盖新增账目。上线后需确认真实带星系消费继续增长、正费用币账一致、0 分证据合法、余额/余量守恒与重复重试不多扣。
